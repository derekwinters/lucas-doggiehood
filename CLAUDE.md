# Doggiehood — Agent Instructions

Doggiehood is a low-poly Android game about a neighborhood of dogs, built by Derek and his son Lucas with Claude doing implementation.

## The contract

**The `/docs` site is the design and architecture contract.** Read it before implementing anything:

- `docs/specs/` — what the game is and does, organized by system. Every page has a "Build checklist" — treat those as acceptance criteria.
- `docs/engineering/` — how the project is built: tech stack, TDD testing strategy, versioning, CI/CD, and this workflow itself.
- `docs/intro/` — vision and conventions, useful context but not itself full of build rules.

Build the docs site locally with `pip install -r docs/requirements.txt && mkdocs serve` if you want to browse it rendered.

**GitHub issues are the checklist for accomplishing the contract.** Each issue carries a detailed TDD-oriented checklist. Work one issue at a time within the current **focus milestone**, lowest issue number first. Milestones are version-numbered planning scopes (`v0.4`, `v1.0`, …), matched live by their description — see `docs/intro/conventions.md`.

If an issue and the docs ever disagree, or something needed isn't covered by either, stop and flag it — don't invent a rule. Decisions get made in conversation with Derek and Lucas, captured as GitHub issues, then reflected in `/docs`.

## Tasks that need Derek or Lucas

Anything an agent cannot complete autonomously — repo settings, secrets, asset creation, unanswered design questions, on-device playtesting — goes in the **`Direct Involvement Needed`** milestone as **one small issue per task**, assigned to Derek, stating the single action needed and how to verify it's done. Never collect human follow-ups into one big multi-section checklist issue.

## Non-negotiable engineering rules

1. **Strict TDD.** Write a failing test, run it, show the failure, implement the minimum to pass, run it, show the pass, refactor if needed. Never write implementation before its failing test exists. See `docs/engineering/testing.md`.
2. **Core/Unity split.** New game logic defaults to a Unity-independent Core C# assembly (plain NUnit, no engine dependency). Only the thin `MonoBehaviour`/scene-wiring layer touches UnityEngine. See `docs/engineering/tech-stack.md`.
3. **Conventional Commits — every commit, every PR title, no exceptions.** Every commit message *and* every pull request title follows [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `chore:`, `docs:`, etc.), going forward from this point on. This isn't optional or best-effort — release-please's versioning depends on it, and a non-conforming commit or PR title should be corrected (amended/retitled) before merging, not left as-is. See `docs/engineering/versioning.md`.
4. **Version lives in `/VERSION`.** Don't hand-edit Unity's `ProjectSettings.asset` version fields; release-please owns `/VERSION`.
5. **Every agent PR carries a `## Deviations and Decisions` section** — the first heading in the body, directly under the plain-English lead (rule #12); mandatory, present even when empty (write "None."). Keep it high-signal, not an exhaustive change-log: include an item only if a reviewer, knowing it, might **act differently** — object, adjust, or follow up. Apply the test to each candidate — *"If the reviewer knew this, would they plausibly do something differently?"* — and if the answer is no, omit it. A 0–2-item list is the norm, and **"None" is a good, common outcome**, not a sign something was missed.
   - **Deviations** — a change that genuinely diverges from the prompt/specs/docs **and** that the reviewer might not expect or might reject; explain each in a sentence or two so they can confirm it's acceptable. *Exclude*: choices the specs/conventions already endorse, self-evident implementation details, restating what the diff plainly shows, "matches the existing pattern," routine test-structure notes, and formatting.
   - **Decisions** — a judgment call made mid-run where there were **real, consequential alternatives** (affecting behavior, scope, an interface, or a design choice) not already settled by the docs/prompt; explain the choice and note how to prevent the gap next time. *Exclude* trivial calls with no meaningful alternative.

   The docs-reconciliation outcome (rule #9) does **not** belong here — it lives on its own `**Docs:**` PR-body line. See `docs/engineering/agent-workflow.md`.
6. **Never guess Unity serialization.** Before hand-authoring `.meta` files or `ProjectSettings.asset` blocks, read `docs/engineering/unity-serialization.md` — verify key names and enum values against real project files (Unity silently ignores unknown entries at build time), pin GUIDs (and Sprite internal IDs) for anything referenced by GUID, and guard the wiring with serialization-level EditMode tests.
7. **Rebase feature branches; don't merge the base back in.** When your working branch's base (e.g. `main`) has moved, bring the branch back into alignment by rebasing it onto the updated base (`git fetch origin main && git rebase origin/main`), not by merging the base into the branch. Keep feature-branch history linear — no `Merge branch 'main' into …` commits.
8. **Wireframe before UI code.** Every UI screen, panel, or overlay requires an approved wireframe (a structured text spec plus a matching HTML mockup) before any implementation code is written — including graybox. If an issue touches a screen's structure and no approved wireframe exists in `docs/specs/ui/`, stop and flag it rather than inventing a layout. See `docs/engineering/ui-design-process.md`.
9. **Every PR reconciles the docs/specs it affects.** If a change adds, removes, or alters behavior, layout, or a design decision, update the relevant `docs/specs` (or `docs/engineering`) page(s) in the **same** PR. Record the outcome on its own dedicated `**Docs:**` PR-body line — **separate** from `## Deviations and Decisions` — e.g. `**Docs:** reconciled in this PR` or `**Docs:** none needed — <reason>`. Keeping this confirmation out of Deviations and Decisions is deliberate: it's a routine compliance line, so it would only dilute that section's high-signal bar (rule #5). CI enforces a conscious decision: the `docs-test` `build` gate runs on every PR and fails a code-only PR unless it carries the `skip-docs` label. See `docs/engineering/agent-workflow.md`.
10. **Close issues with a GitHub closing keyword.** Every commit or PR that fully resolves an issue must carry a GitHub closing keyword — `Closes #N` (`Fixes #N`/`Resolves #N` are equivalent) — so that merging auto-closes the issue. A bare `Refs #N` only links, it does not close, and leaves the issue stuck `open`/`in-progress` after merge. If a PR iterated and no commit ended up with the keyword, add it in the PR body or an empty follow-up commit before merge. See `docs/engineering/agent-workflow.md` and `docs/engineering/versioning.md`.
11. **Hard blockers are native, never prose.** A hard dependency ("issue A is blocked by issue B") is recorded as a **native GitHub issue-dependency relationship** using the `issue-blockers` skill (`.claude/skills/issue-blockers/`) — not a `Blocked by #N` line in an issue body or comment. Prose-only blockers are flagged as drift by the reconcile sweep (`flag_prose_dep`) and are invisible to native tooling; if you find one, convert it with the skill and remove the line. (Soft ordering — `Depends on: #N` — has no native GitHub form and stays a structured text line; don't try to nativize it.) See `docs/engineering/issue-pipeline.md`.
12. **Lead in plain English, and let specs rule out bad solutions.** Three habits that go together — a fix can be technically correct and still be the wrong fix, and both the spec and the write-up have to make that catchable *before* it ships ([#545](https://github.com/derekwinters/lucas-doggiehood/issues/545)):
    - **Plain-English lead — first thing in every write-up.** Every triage analysis, implementation note, and PR body opens with a direct **2–3 sentence** summary: what's wrong and what we're changing, in words that are easy to skim, **before** any class names, file paths, or TDD detail. The technical content still follows in full; it just doesn't come first. In a PR body the lead is an un-headed paragraph sitting above `## Deviations and Decisions`, which stays the first *heading* (rule #5).
    - **Specs state invariant rules, not only outcomes.** Wherever a system could be built in a way that is technically-correct-but-wrong, the spec carries an explicit **invariant** — a short imperative sentence constraining *how* it may work ("A delivery truck never leaves the roadway.") — so the bad solution is off the table up front, not argued about after the fact. When a bug's root cause is a *missing* rule rather than a coding mistake, triage proposes the rule and its Build checklist includes a test for it. Follow the existing `**Invariant — …**` paragraph style in `docs/specs/quests/quest-content.md`.
    - **Every spec change carries a "how the spec is changing" note.** When a PR (or a triage plan) alters what a spec page *says* — as opposed to purely adding new, previously-uncovered content — the spec page gets a plain-English **`> **How the spec is changing (#N).**`** blockquote: *what it used to say → what it now says → why*. It's the human-readable record of the design shift, deliberately separate from the technical diff, from `## Deviations and Decisions` (rule #5), and from the `**Docs:**` line (rule #9). Same precedent page as above.

    See `docs/engineering/agent-workflow.md` and `docs/engineering/issue-pipeline.md`.
13. **No development without an approved issue — enforced mechanically.** Code, tests and build configuration are only edited in service of an issue that has already been triaged and approved. A bug report, a screenshot, or "this is still broken" is **not** authorization to start building: file or find the issue, get it approved, and only then write code. This is enforced by a `PreToolUse` hook (`.claude/hooks/issue_gate.py`), not left to judgement — `Edit`/`Write`/`MultiEdit` against `Assets/**`, `CoreTests/**`, `ProjectSettings/**` or `Packages/**` is **denied** unless `DOGGIEHOOD_APPROVED_ISSUE` names an issue whose **live** GitHub labels include `ready-for-work` or `in-progress` (the two post-approval states; `in-progress` is only reachable from `ready-for-work`, and the builders set it before writing any code). Docs, `.claude/**`, issue filing and every read-only tool stay unblocked, so triage and investigation still work. Setting the variable to an issue you haven't had approved doesn't help — the check is against GitHub's live label state, and passing the gate is not a substitute for actually having the work approved. See `docs/engineering/agent-workflow.md`.
14. **Wide changes need confirmation before the first edit.** Before making a change that touches **more than 5 files**, or that touches `CLAUDE.md`, any `docs/engineering/**` page, or `.claude/settings.json`, or that renames/renumbers something across **3 or more files**, state the approach and its blast radius and **wait for explicit confirmation**. A narrow request does not authorize a wide implementation of it: when a churny approach and a contained one both satisfy the ask, surface the choice rather than picking the churny one. (The motivating case: told to add one `CLAUDE.md` rule, an agent renumbered the whole list and rewrote 24 cross-references across 13 files — which is why new rules are **appended**, never inserted.) See `docs/engineering/agent-workflow.md`.

15. **Never publish a private link.** Session links, signed URLs, share and invite links, anything carrying a token in a query string — none of it goes into a workflow log, an issue, a pull request, a commit message, or a comment. This repository is public, so all five are publications, and an identifier published once cannot be unpublished. The test is not *"is this a credential"* but *"would I post it in public"*, and a link that exists to reach something private fails that test whether or not a login stands behind it. Say **that** the thing happened and let whoever owns it look it up — `fired Routine for #123` is as useful as the link and costs nothing. This applies to text the code did not author: error messages, response bodies and stack traces quote the values they were handed, so a branch that echoes a raw body needs redaction rather than trust. That is where the motivating leak hid — the deliberate log line was fixed while the failure branch went on publishing the same link ([#735](https://github.com/derekwinters/lucas-doggiehood/issues/735)).

## What not to do

- Don't add monetization, ads, accounts, or network calls — the product is free, offline, local-save-only (`docs/specs/product-scope.md`).
- Don't invent quest types, personalities, breeds, or mechanics not in the specs — bring new ideas back to Derek and Lucas first.
