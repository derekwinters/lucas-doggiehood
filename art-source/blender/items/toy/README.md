# Dog toy: squeaky plush duck (#332)

The "toy" a dog can lose (#928) or be given (#929) is today a plain white graybox sphere
(`LostItemView`). This folder builds a real one: a **blue squeaky plush duck with an orange bill
and feet**. It is generated by a Blender Python script run headless, with no hand modelling, and
follows [`docs/engineering/blender-pipeline.md`](../../../../docs/engineering/blender-pipeline.md).
It is a **source asset only**: nothing here is imported by Unity (the folder is outside `Assets/`),
and it waits for Derek to approve the renders on #332.

## Why a plush duck

Which toy to make was left as a taste call. I picked the plush duck because it reads best at the
lost item's small size from the 45° camera:

- **Its outline is its own.** A sitting duck (round head over a body that tapers up into a tail,
  with a bill sticking out) is nothing like the ball (#333, a sphere) or the chew bone (#923, a bar
  with knobbed ends), even when it is only a few dozen pixels on screen.
- **It says "toy" at a glance.** A plush duck is a classic squeaky dog toy, and its toy colours
  make it read as a toy, not an animal. A plush dog, fox or squirrel could be mistaken for the lost
  puppy, which is another subject of the same quest.
- **Its colours stand out on both surfaces.** Blue with an orange bill and feet is not the lawn's
  green, the sidewalk's light grey, the tennis ball's yellow-green, or the red of the lost-item
  finder ring (#602). On grass and on the sidewalk the toy stays a clear blue shape with an orange
  accent (see the renders).

I also considered two rope toys and rejected them. A **rope tug** with a knot at each end has the
same knobbed-bar outline as a chew bone. A **rope ring** looks like the red finder ring drawn under
every lost item. If Derek prefers another toy, the script is the only thing that changes.

## Size and budget

| | |
|---|---|
| Size (W × L × H) | **0.33 × 0.54 × 0.40 m** (bill tip to tail 0.54 m, top of head 0.40 m) |
| Triangles | **1,608**, one mesh, no LOD |
| Budget | Within the provisional 6,000-triangle per-mesh backstop of the art budget (#799) |
| Materials | `DH_Toy_plush_blue` (body, head), `DH_Toy_plush_navy` (wings), `DH_Toy_plush_orange` (bill, feet), `DH_Toy_eye_white`, `DH_Toy_eye_black` |
| Textures | `toy_fleece_color.png` and `toy_fleece_normal.png`, 256², shared by the three plush materials and tinted by each one's `baseColorFactor`. The eyes are plain colour |
| Export | `exports/toy_duck.gltf` (7.9 KB) + `toy_duck.bin` (45 KB) |

**How big it is next to a dog.** Dogs in this world are about 1.8 times real size: the approved
adult Labrador is 1.58 m to the top of its head and 1.04 m at the back, where a real Lab is about
0.57 m at the shoulder. A real plush duck toy is about 30 cm long, so at the same scale it is about
0.54 m. That is about the size of today's 0.6 m graybox sphere, so the lost item takes up about the
same space on screen as before.

## Conventions (for #928 and #929)

These are the same as the street props:

- 1 Blender unit = 1 m at in-game size, so the game places it at **scale 1**.
- The front (the bill) faces −Y in Blender, which is +Z in the glTF (exported with `export_yup`).
  Up is +Z in Blender.
- **Pivot on the ground at the centre of the footprint.** The underside is flat at z = 0, so the
  toy sits on the surface at its placement point. The graybox sphere's `SphereGroundHeight` offset
  doesn't apply to it.
- Transforms are applied on export. There is one node and one mesh, both named `toy_duck`.
- The plush materials are single-sided (every part is a closed shape).

## Files

```
items/toy/
  dh_toy_tex.py      the fleece texture pair (numpy + PIL, fixed seed 332, tileable)
  dh_toy.py          the model: DIMS-style named parts, colours, build(), TRI_BUDGET
  export_toy.py      writes the textures, exports/toy_duck.gltf + .bin and exports/toy_stats.json,
                     reads the glTF back and exits non-zero if a check fails
  render_toy.py      the review renders and the web-viewer .glb, to out/ (git-ignored)
  tests/test_toy.py  budget, pivot, read-back and byte-for-byte rebuild checks
  textures/          toy_fleece_color.png, toy_fleece_normal.png
  exports/           toy_duck.gltf + toy_duck.bin (images by relative URI ../textures/), toy_stats.json
  review/            the review renders below
```

The model is built from ellipsoids, each with its own named centre, radii and segment count in
`dh_toy.py`. The script builds them in a fixed order itself. `bmesh.ops.create_uvsphere` was not
used: in `bpy` 5.3.0 it gives a different face winding order from run to run, so the exported
`.bin` changed every build.

## Review renders

| File | What it shows |
|---|---|
| `review/toy-grass.png` | The toy on the approved lawn beside the approved adult Labrador (yellow coat) in front of base house 1, at the game camera (ortho, pitch 45°, yaw −40°). Three panels: the whole screen at the closest game zoom (`CameraController.MinZoom`, 6 m half-height) at 1:1 on a 1920 × 1080 landscape screen, a 1:1 crop at the default zoom (`DefaultZoom`, 18 m), and a closer view (1.3 m, closer than the game allows) |
| `review/toy-sidewalk.png` | The same on the approved sidewalk (paving set 1, road kit A) |
| `review/toy-closeup.png` | The toy from the game angle, a low front 3/4, the side and the top, beside today's 0.6 m graybox lost-item sphere, with a 10 cm scale bar |

At the closest zoom the toy is about 50 px long and reads as a blue duck with an orange bill. At
the default zoom it is about 16 px, a small blue shape with an orange accent. It is not lost against
either surface there, and the red finder ring (#602) marks it anyway.

`render_toy.py` also writes `out/glb/toy_duck.glb`, a self-contained copy with the textures
embedded, for a three.js viewer. It is not committed: the `exports/` glTF is the source of truth.

## Regenerating

From the repository root, with headless Blender as a Python module (`pip install bpy==5.3.0`) plus
numpy and Pillow:

```
python3 art-source/blender/items/toy/export_toy.py                 # textures + exports + stats, a few seconds
python3 art-source/blender/items/toy/render_toy.py [OUT_DIR] [--views grass,sidewalk,closeup,glb] [--samples 48]
python3 art-source/blender/items/toy/tests/test_toy.py             # about 5 s
```

`export_toy.py` prints `ALL OK` when every check passes. Two runs in fresh processes write
byte-identical textures, exports and stats. The test rebuilds twice into a temporary folder and
compares both with the committed files. The renders read the approved lawn, road, paving, house
and Labrador exports from `art-source/blender/` by relative path. They are not byte-reproducible,
and in a container without a GPU EEVEE runs on Mesa's lavapipe. The glTF exporter prints harmless
`Draco` / `MeshOptimizer` library errors (neither is used).
