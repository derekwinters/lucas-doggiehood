    Neighborhood Expansion¶

    Epic: #55

    v0.4

    This entire system is fully designed and is now slated for v0.4 (#88) — no longer deferred. The neighborhood still starts with just the 4 houses (see World & Neighborhood); nothing on this page gets built before v0.4 starts.

    The loop¶

    1. Unlock a zone: the player pays a currency cost to unlock a new zone/area of the map. Newly unlocked zones start with no houses at all — just empty land. (#56)
    2. Build houses: the player spends currency to construct individual houses within an unlocked zone. Houses don't appear automatically — building each one is its own purchase. (#57)
    3. Vacancy: a freshly built house is empty and renders greyscaled until a dog eventually moves in. (#58)
    4. Occupancy over time: new dogs arrive and move into empty houses gradually over time, rather than all at once. (#54) See Move-in system below for the full mechanism, and Dog Roster & Names for how names and breeds are drawn.
    5. House leveling: every house starts at level 1 and can be upgraded up to level 4. Upgrading makes the house visually bigger/nicer and increases how many decorations its yard can hold. (#59)

    Map shape¶

    Decision (2026-07-31, Derek, on #295) — player-choice single-tile frontier, superseding the sequential-zone model below. The unlock unit is a single tile, not a hand-grouped zone, and the order is the player's choice. Any placed tile's open road edge that borders a tile defined in the full authored target map (docs/tools/map-data.json, #383) and not yet placed is an unlockable frontier coordinate — shown with a lock icon the player can tap to unlock if they can afford it. The frontier is derived algorithmically from (placed map) vs (target map) using #109 edge-adjacency — exactly what TileMap.CanPlace already checks — so no manual grouping/carving is authored. Onboarding gate: before the onboarding reward-chain's step-3 "expand the map" completes, only that one scripted tile is unlockable; after it completes, every current frontier tile is simultaneously unlockable, in any order. This supersedes the "unlock authored zones in sequence" model described in the 2026-07-14 decision immediately below and its ZoneCatalog-list implementation. The multi-lock indicator rework (one lock per open connection point) shipped in #453, which also RETIRED the legacy sequential path outright — ZoneCatalog, Zone/ZoneTilePlacement, TryUnlockNextZone, ZoneUnlock/ZoneUnlockNumbers/ZoneUnlockOffer, RestoreUnlockedZoneCount, and the single-marker indicator (ExpansionIndicator.Resolve(state), ExpansionIndicatorPlacement.Resolve(map, zone)) are all deleted. Frontier tiles now cover the same ground: the Unity layer supplies the authored target map at runtime (MapDataLoader loads Assets/Resources/Data/map-data.json and calls SetTargetMap at bootstrap), each frontier tile's lots get stable house ids from a pure FrontierHouseId.For(coordinate, quadrant) function, and ExpansionUnlockDirector maintains one lock indicator per unlockable frontier coordinate. Old saves are not carried across this change (a legacy zones=N line is simply no longer understood); the onboarding single-tile gate (only (0,1) unlockable until the "expand the map" step completes) is unchanged.

    Decision (2026-07-14, Derek, on #86) — superseded for unlock unit/order by the 2026-07-31 decision above; still current that expansion is authored, not procedural. the map is hand-picked expansion with no fixed end — tiles are authored and added over time, and procedural generation stays out of scope (#109). The authored tiles come from the tile catalog (60m grid), pre-authored by Derek and Lucas; the player never freely places arbitrary tiles — they only unlock tiles the authored target map already defines. Early tiles use only cul-de-sac, straight, tee, and turn tiles — more variety (including the OpposingTurns/park-island tiles, whose arch-loop question stays deferred on #109) comes later. (Original wording: a zone was a hand-authored group of tiles unlocked in sequence; the 2026-07-31 decision replaced the group with a single tile and the sequence with player choice.)

    First zone: a single cul-de-sac directly north of the starting intersection. The confirmed layout (2026-07-29, Derek, on #360): from the starting FourWay at grid (0,0), a single CulDeSacSouth tile at (0,1) — its road enters from the south edge (meeting the origin FourWay's north road) and ends in a bulb pointing north, so the whole zone sits due north with no dangling roads. This supersedes the earlier two-tile northwest layout (2026-07-14, Derek, on #56: TurnSW at (0,1) + CulDeSacEast at (−1,1), which ran north then turned west into the bulb) — the single north tile also lines up straight under the expansion lock indicator, which already hovers due north of the origin.

    The tile-grid placement/adjacency system this all sits on is #109, the milestone's geometric prerequisite.

    Implementation note (#383) — the authored target map is loadable in Core. The full neighborhood Derek & Lucas authored in the Map Builder (84 tiles, committed as design data at docs/tools/map-data.json, shaped {name, tiles:[{x,y,type}]} with x→Col, y→Row and origin FourWay at (0,0)) parses into a validated Core TileMap via Doggiehood.Core.World.MapDefinition.Parse + MapLoader.Load, exposed as the neighborhood's target/full layout. Placement is self-ordered — the file lists tiles in authoring order, not adjacency order, so the loader seeds the origin then repeatedly places any pending tile that already has a placed neighbour (through #109's TileMap.CanPlace/Place) until nothing more can be placed; a tile that fails adjacency is reported in MapLoadResult.RejectedCoordinates, never thrown. MapLoadResult.CurvedCorners gives, per bend (Turn*) tile, the Quadrant corner that renders curved (data only — no rendering yet). This is Option A of #383: the loader produces the target map as Core data; the live playable world stays incremental (seeded FourWay, grown one tile at a time). The target map is now the reference the player-choice frontier unlock (#295) reads: GameState.SetTargetMap supplies it, and Doggiehood.Core.Expansion.TileFrontier.Compute(placed, target) derives the unlockable coordinates from it — see the #295 note under Pricing.

    Pricing¶

    Decisions 2026-07-14 (Derek, in conversation). All values are named, tunable constants in Core — expect adjustment during playtesting; see also Quest & Economy.

    Purchase Cost
    Tile unlock (frontier) 100 coins, flat per tile (#295) — a single swappable cost function (TileUnlock.Cost), so a future per-existing-tile scaling (Derek's "+10 per existing tile") is a one-place change. Supersedes and (as of #453) fully replaces the earlier escalating zone-unlock formula (100, 200, 300, …); the ZoneUnlock path is deleted.
    Build a house 50 coins, flat
    House upgrade to L2 / L3 / L4 100 / 200 / 400 coins (doubles per level)

    Implementation note (#56) — HISTORICAL; the Zone/ZoneCatalog sequential-unlock machinery below was RETIRED by #453. It is superseded end-to-end by the player-choice frontier (TryUnlockTile, FrontierHouseId, UnlockedTiles) described in the #295 and #453 notes above; the classes named here (Zone, ZoneCatalog, ZoneUnlock, TryUnlockNextZone, RestoreUnlockedZoneCount) no longer exist. Kept for provenance: built as pure Core logic on top of #109's tile grid — Doggiehood.Core.World.Zone (authored tile placements + the quadrant lots each tile carries, via TileLotCatalog/TileGeometry), Doggiehood.Core.World.ZoneCatalog (the authored zone list — only the first zone exists yet), and Doggiehood.Core.Expansion.ZoneUnlock/ZoneUnlockNumbers for the cost formula. GameState now owns a TileMap (Map, seeded with just the starting FourWay intersection) and UnlockedZones; GameState.TryUnlockNextZone() is the one entry point — it charges Wallet for the next zone in sequence, adds that zone's tiles to Map through #109's placement/adjacency validation, and returns false with no state change (no deduction, no tiles placed) if the balance can't cover it or every authored zone is already unlocked. Unlocking never creates House objects — GameState.IsLotBuildable(houseId) reports a zone's lots as buildable exactly because no House exists for that id yet, which is what house building (#57) checks. Persistence (#343): Map/UnlockedZones now round-trip through SaveCodec so an unlocked zone survives an app relaunch. Because zones are authored and deterministic (ZoneCatalog), the save stores only the unlocked count (zones=N); on load GameState.RestoreUnlockedZoneCount replays the first N authored zones onto Map/UnlockedZones without re-charging the wallet or re-advancing the reward chain (the parallel of RestoreRewardChainStep). A legacy save with no zones line loads as nothing unlocked.

    Implementation note (#295) — the player-choice frontier unlock (supersedes the sequential zone unlock above). Built as pure Core logic: Doggiehood.Core.Expansion.TileFrontier.Compute(placed, target) returns every coordinate that (a) borders an already-placed tile, (b) exists in the authored target map, and (c) isn't already placed — reusing #109 edge-adjacency the way TileMap.CanPlace does, so a tile is on the frontier only if it would place validly (its road/no-road edges agree with every placed neighbour), which is Derek's "a road with a connection point that has another tile defined". GameState gains the authored TargetMap (supplied by the Unity layer via SetTargetMap; not itself persisted — fixed design data re-supplied each launch), UnlockedTiles (the coordinates unlocked one-at-a-time), and UnlockableFrontier() (the frontier gated by onboarding: only the single scripted OnboardingExpansionTile — the authored first tile at (0,1) — until the reward-chain "expand the map" step completes, then the whole frontier at once). GameState.TryUnlockTile(coordinate) is the one entry point — it charges the flat Doggiehood.Core.Expansion.TileUnlock.Cost(placedTileCount) (a single, named, swappable function returning TileUnlockNumbers.BaseCost = 100 today; the tile count is threaded through so a future scaling formula is a one-line edit), places the chosen frontier tile through #109's validated TileMap.Place, and advances the onboarding "expand the map" step; it returns false with no state change (no deduction, no tile placed) when the coordinate isn't a currently-unlockable frontier tile or the balance can't cover the cost. Persistence: unlocked tiles round-trip through SaveCodec as the actual set of unlocked coordinates (tile=col|row|type, emitted in unlock order), superseding the sequential zones=N count for the frontier path; on load GameState.RestoreUnlockedTile replaces each onto Map without re-charging the wallet. #453 wired the Unity layer to this frontier model (multiple simultaneous locks, one per open connection point) and deleted the legacy zones=N/TryUnlockNextZone/ZoneCatalog path — see the #453 note under Frontier-tile lots and the map-shape decision above.

    Frontier-tile lots and house ids¶

    Implementation note (#453) — frontier tiles grow buildable lots. A player-unlocked frontier tile carries the quadrant lots its type defines (TileLotCatalog.LotsFor, already generic across the 16 non-FourWay types), positioned from the tile centre and given a stable, collision-free house id derived purely from (coordinate, quadrant) via Doggiehood.Core.World.FrontierHouseId.For (zig-zag-encode col/row, Cantor-pair them, * 4 + quadrantIndex, plus a fixed base offset clear of the 4 starting ids). Because the id is a pure function of position — not a replayable counter — the mapping needs no extra persistence and survives player-chosen unlock order. GameState.IsLotBuildable/GetHouseLot/TryBuildHouse resolve a frontier tile's lots (via GameState.LotsForUnlockedTile) exactly as they already do for a starting lot, and TryUnlockTile rolls + persists each new lot's HouseVariant at unlock (the frontier equivalent of the retired AssignZoneLotVariants), so an empty frontier lot renders its predetermined ladder/tint and pre-baked yard trees immediately. Every frontier id is ≥ HouseVariantAssignment.FirstZoneHouseId, so it rolls a variant like any zone house did.

    Implementation note (#57): GameState.TryBuildHouse(houseId) is the one entry point — it charges Doggiehood.Core.Expansion.HouseBuildNumbers.Cost (50 coins, flat) from Wallet and adds a new House at House.InitialLevel (1) and vacant, returning false with no state change when the lot already has a house (IsLotBuildable false), the lot's zone hasn't been unlocked yet, or the balance can't cover the cost. GameState.GetHouseLot(houseId) resolves a house's lot across both the starting layout and any unlocked zone, for the Unity layer. On the Unity side, WorldBuilder.BuildEmptyLots renders one graybox marker (EmptyLotView) per buildable lot in every unlocked zone; ExpansionDirector wires each marker's tap to the reusable confirmation dialog (Building a house first asks, #406): a tap resolves Doggiehood.Core.Expansion.HouseBuildOffer.Resolve(state, houseId) (null when the lot isn't buildable — a no-op that never opens the dialog) and raises the dialog with "Build a house here?" + the flat 50-coin cost on Yes; only Yes calls TryBuildHouse, and on success replaces the marker with the real house visual (WorldBuilder.BuildHouse) and saves — No/scrim cancels with no spend. A mid-game build now also renders the lot's yard and fence (#405): after BuildHouse, ExpansionDirector calls the single-lot render helpers WorldBuilder.BuildYardLandscaping(lot) / BuildFence(lot) / BuildWalkway(lot) (extracted from the world-build loops), so a zone house gets its yard trees — and its fence when fences are visible — the same treatments a starting house gets at world-build time, instead of only its bare mesh. The full world-build and debug-toggle fence loops cover zone houses too (#424): WorldBuilder.BuildFences/RebuildFences iterate every built house via GameState.GetHouseLot rather than the starting-only NeighborhoodLayout.HouseLots, so a zone house is fenced on a fresh world build and when the #219 debug toggle rebuilds fences — not only at the moment it is built. The fence still stays hidden by default (HouseLot.HasFence off); #424 only makes the geometry exist and build for every house. A zone house now also faces the street with a real front walkway (#430) — the front-walkway/street-facing piece is no longer deferred. GameState.WalkNetwork admits a built zone house's lot (its filter widened to accept a house with an authored style or a rolled HouseVariant), so the lot grows a real front-walkway edge; the render path builds against that live network (ExpansionDirector and WorldBuilder.Build pass state.WalkNetwork into BuildHouse/BuildWalkway, calling the network-aware HousePlacement.FrontFacing(lot, network) overload) instead of the starting-tile-only NeighborhoodLayout.WalkNetwork, so the zone house renders facing its street with a tiled walkway to the door — a starting-house treatment — rather than the old Z-sign facing fallback / BuildWalkway no-op. A zone house's fence and yard trees now rotate with it too (#461): #430 threaded the live-network facing into the house mesh and its walkway only, so the fence (via the debug toggle) and the pre-baked trees still used the pre-rotation Z-sign fallback and sat at the old orientation. LotFence.GeometryFor(lot, state) now reads state.WalkNetwork for the fence's facing/position, and the yard-tree pre-bake (WorldBuilder.BuildEmptyLots/RenderUnlockedTile → the BuildYardLandscaping(lot, tileType, network) overload) threads that same live network so a zone lot's trees orient to the house's real street-ward facing. Because trees are baked at unlock before any walkway edge exists (below), the tree/fence path resolves the predetermined facing by projecting the lot centre onto its nearest sidewalk (HousePlacement.PredeterminedFrontFacing/PredeterminedPosition), which on this axis-aligned map equals the walkway-derived facing the build later resolves — so the pre-placed trees stay correct and are never regenerated (a Core test locks predetermined == actual, protecting #434's no-regenerate assumption). Letting the lot into WalkNetwork also puts its walkway on the graph dogs path over; a resident-only wander gate keeps every other dog off it (see the walk network and Dog Behavior pages). Dogs entering the house / passing through to the backyard stays out of scope (a possible later follow-up). A stray tap no longer spends coins, so building now mirrors the zone-unlock spend (both go through the same "are you sure?" dialog); the currency HUD reflects a confirmed build automatically since it reads Wallet.Coins live every frame. (House upgrade stays deliberately confirmation-free — Derek's Option A, #294 — so building is confirmed while upgrading is a direct spend.) Empty-lot marker look (settled, #300 (B), Derek; revised by #434): the marker is a low raised graybox "foundation" slab that reads as "a house goes here" — a single primitive box (WorldBuilder.EmptyLotFoundationSlabHeight tall, base flush on the ground plane, painted Palette.EmptyLotMarkerHex), no new kit asset. Its X/Z footprint is now sized to the predetermined house's level-1 mesh footprint (HousePlacement.HouseFootprint(lot)) and centred on it (#434), reversing the earlier #300 option-3 fixed-marker size (WorldBuilder.EmptyLotMarkerFootprint, now removed). #300's reasoning — "an empty lot has no built house (no rolled model) to size a footprint from" — no longer holds: since #414 HouseModelCatalog.ForHouse is zone-aware (it resolves the rolled ladder's level-1 mesh instead of throwing for a zone lot id ≥ 5), and since #434 the variant is rolled and persisted at unlock (below), so an empty lot does know its future house. The lot also pre-places its yard trees at unlock (#434): the empty-lot render sites (WorldBuilder.BuildEmptyLots on the initial build, RenderUnlockedTile on a mid-game unlock) call the deterministic WorldBuilder.BuildYardLandscaping(lot) too, so an empty lot shows trees + a house-sized foundation, not a bare box. Building the lot then swaps only the foundation slab for the house mesh — the already-rendered trees are left in place (ExpansionDirector.ConfirmBuild deliberately does not re-render them), so there are no duplicates. Houses built this way have no authored HouseStyleTable entry (that table only covers the starting 4). Their look is designed and implemented (#299, Derek 2026-07-28; timing moved earlier by #434): each zone house rolls its own model ladder (one of five) and tint (one of a generated 20-color palette) via a deterministic seed on its house id (Doggiehood.Core.Art.HouseVariantAssignment), assigned when its tile unlocks (GameState.TryUnlockTile, stored in GameState.AssignedLotVariants) rather than lazily at build (#434), and persisted (ladder id + tint index) through SaveCodec (a lotvariant= line for an assigned-but-unbuilt lot; a built lot's variant rides its house= line) so it survives relaunch and L1→L4 upgrades. TryBuildHouse reads that pre-assignment; a legacy save whose zone predates #434 has no persisted entry and falls back to the same deterministic HouseVariantAssignment.ForHouse roll — bit-identical, since the roll is a pure function of the house id. WorldBuilder.BuildHouse renders the rolled ladder's current-level mesh and multiplies the palette tint over it (ApplyPaletteTint); the graybox fallback is now reached only when the kit model can't load or a house carries no rolled variant. See Art Style → House architecture for the full rule. The player-facing zone-unlock trigger ships in #343 — see Expansion indicator below.

    Move-in system¶

    Decision 2026-07-14 (Derek, in conversation), detailed on #54. All values named, tunable constants; RNG injectable for deterministic tests.

    • Trigger — quest-completion pity counter, shared: every completed quest rolls a single shared move-in chance: base 5%, +5% per completed quest without a move-in, reset to base on success. One counter for the whole neighborhood; on success one vacant house is chosen at random (uniform). The counter only advances while at least one vacant house exists.
    • Households: roster-style mix from day one — 70% single / 25% parent+puppy / 5% three-dog. Parent+puppy pairs share a breed; every dog gets its own personality, randomly drawn from the behavior set.
    • Breeds: the reserved French Bulldog and Puggle are the first two move-ins; afterwards breeds are chosen by count-weighted randomness — each breed weighted inversely by how many currently live in the neighborhood, so variety self-adapts to the existing distribution.
    • Easter eggs: each move-in has a 5% chance the household head is an easter-egg dog (fixed breed/coat, breed roll skipped); once used, an easter-egg name is permanently removed from the reserve — each appears exactly once.
    • Names come from the general name pool, no duplicates among active dogs.
    • New dogs join the daily quest rotation immediately.
    • Announcement: a move-in raises a "Welcome to the neighborhood!" celebration pop-up (one per household) — see the welcome pop-up wireframe for the layout, its per-dog member-chip row, timing, and the "Say hi!" camera pan.

    Implementation note (#54/#58): the mechanism above is built as pure Core logic — Doggiehood.Core.Expansion.MoveInSystem, VacantHouses, and BreedWeighting — operating on an abstract set of vacant house ids plus the current dog roster, with no dependency on the #109/#56 tile-grid/zone geometry. Doggiehood.Core.World.House carries the vacancy flag itself (IsVacant, flipped by MarkOccupied); Doggiehood.Core.Expansion.HouseOccupancy bridges the two, deriving the current vacant set from live houses, running one MoveInSystem roll, and — only on success — occupying the filled house. GameState.HandleQuestCompleted calls this on every completed quest (QuestManager.Complete), so the trigger is fully wired. Since zone unlock (#56) and house building (#57) don't exist yet, every house in a real game is one of the 4 starting houses (already occupied at GameState.CreateNew()) — so this wiring has no vacant house to actually fill until #56/#57 land, but is exercised directly in the Core test suite. Persistence (#437): MoveInSystem's pity counter (quests-since-last-move-in, i.e. the accumulated move-in chance) and its consumed easter-egg / reserved-breed reserve now round-trip through SaveCodec — a single moveIn=<questsSinceLastMoveIn>|<remaining easter-egg names>|<remaining reserved breeds> line (breeds stored by name; a reserve segment is empty once exhausted). On load GameState.RestoreMoveInState rebuilds the system from those saved values without rolling any dice or firing a move-in (the parallel of RestoreRewardChainStep); a legacy save with no moveIn= line keeps CreateNew's default fresh system (base 5% chance, 0 quests, full reserves). So move-in odds no longer reset to the base and a used easter-egg name never reappears across an app relaunch.

    Implementation note (#436) — a move-in is reflected in-game the instant it happens. The Core mechanism above filled a vacant house but was invisible during play: QuestManager.Complete discarded HandleQuestCompleted's returned household, so the Unity layer never learned a dog had moved in — no DogView appeared and the filled house stayed greyscaled until a full world rebuild. Core now surfaces the event: QuestManager raises public event Action<IReadOnlyList<Dog>> MoveInOccurred from the single Complete funnel, right after HandleQuestCompleted, only when the returned household is non-empty — so all three completion paths (delivery, lost-item find, spray) are covered for free. On the Unity side QuestDirector subscribes in Init and, on each move-in, (a) spawns a DogView for every new resident — bound to the filled houseId, tappable and wandering — through the extracted DogSpawner.SpawnDog(state, parent, dog, indexAtHouse) (the per-dog body of the build-time SpawnDogs loop, so the live and build paths share identical house-lookup/stagger/DogView.Init wiring) without touching or duplicating any existing DogView, and (b) drops the filled house's vacancy greyscale (#58) by calling HouseUpgradeDirector.RefreshHouse(houseId) — the same destroy-and-rebuild the #407 upgrade path uses, which re-derives the mesh from the same Core House/HouseLot and so preserves the house's rolled variant/tint while the now-occupied flag makes the rebuild pick the normal tint instead of the grey. WorldBootstrap builds the HouseUpgradeDirector up front (moved earlier than #407's original profile-overlay closure) so QuestDirector.Init can hold a reference to it; its rebuild-callback (tap re-wiring) is still configured in BuildHouseProfileOverlay, which runs before any quest can complete. No save-format change — SaveStore/SaveCodec already persist Houses/Dogs, so a live move-in already round-trips; this issue is purely the immediate on-screen reflection.

    House leveling¶

    Levels 1–4. Decoration slots equal the house level (1/2/3/4); upgrade costs are in Pricing (100 / 200 / 400, doubling per step, capped at level 4).

    Per-level visuals — model swap (#59, Derek 2026-07-25). Leveling a house up swaps its City Kit Suburban mesh for the next rung of a per-house ladder, so a home visibly grows as it is upgraded. Each ladder is anchored on its Level-1 mesh — the level-1 entry is exactly the as-built mesh HouseStyleTable assigns that house, so a level-1 house renders identically to today. The approved L1→L4 ladders:

    House L1 L2 L3 L4
    1 building-type-r building-type-c building-type-s building-type-b
    2 building-type-h building-type-i building-type-g building-type-f
    3 building-type-k building-type-l building-type-j building-type-d
    4 building-type-q building-type-e building-type-u building-type-n

    A 5th ladder for zone-built houses (#299). Houses the player builds on zone lots (id ≥ 5) don't have a fixed per-house ladder — they roll one of five ladders (the four starter ladders above plus a 5th, HouseLevelModelTable id key 5, size-ordered L1→L4 building-type-o → building-type-p → building-type-a → building-type-m) and one of a generated 20-color tint palette, seeded deterministically on the house id and persisted across upgrades. Leveling still swaps the mesh up the rolled ladder exactly as it does for a starter. The full rule (assignment, persistence, palette generation, color-multiply tint) is in Art Style → House architecture and the #57 build note above.

    All four levels render their chosen kit mesh (v0.6 de-graybox pass, Derek's directive "I want the house models we chose at all levels, not graybox"). Every rung of every ladder now has a full HouseModelCatalog entry, so an upgraded house shows its real City Kit Suburban mesh — never the graybox placeholder. Houses render at one fixed uniform kit scale (HousePlacement.KitScale, no per-model normalization), so a bigger mesh renders bigger: the size growth is real, and every ladder mesh's footprint still fits the shared lot envelope the starters already occupy at that scale, so leveling never resizes or moves the lot — its quadrant bounds and hand-picked centre are untouched. The house visual on that lot does re-align each level, though (#454): a taller/deeper upgrade mesh has a different footprint depth, so its front-setback pivot, its HousePlacement.HouseFootprint rect, and the front walkway that meets its door are all resolved from the house's current level's model (HouseModelCatalog.ForHouse(houseId, level), threaded through HousePlacement.Position/PositionFor/HouseFootprint), keeping the upgraded facade exactly FrontSetback from the sidewalk instead of drifting off the level-1 calibration. HouseUpgradeDirector.RefreshHouse re-aligns all three together — it rebuilds the mesh at the level-aware pivot and calls WalkNetwork.RefreshFrontWalkway(lot, level) so mesh, visible door, and walkway agree at the new level. (The earlier note that placement was resolved from the level-1 mesh regardless of level — the ZoneHousePlacementLevel shortcut — held only for the level-blind HouseModelCatalog.ForHouse(houseId) overload, still used where no level is in hand.) Core carries only mesh-name strings (Doggiehood.Core.Art.HouseLevelModelTable); the geometry lives in HouseModelCatalog. The only thing still deferred is the front-door anchor of each non-L1 ladder mesh (and the r/h/q L1 starters): those are provisional placeholders (centered on X, z = −FootprintZ/4, strictly inside the footprint) pending a gallery authoring pass — the models themselves are final, and the walkway re-aligns to whatever anchor each level's model carries (provisional or final). The graybox fallback still exists, but is now reached only when the kit model can't load or a house carries no resolvable ladder (a zone house with no rolled variant, or an unknown expansion id) — since #299, an ordinary zone-built house resolves its rolled ladder and renders a real kit mesh.

    Decoration capacity = house level. A yard holds at most as many decorations as its level (1/2/3/4); a placement past capacity is rejected. See Decorations for the cap and its grandfathering rule (yards that already held more than their level's cap when this shipped keep everything — the cap blocks new placements only).

    Implementation note (#59): GameState.TryUpgradeHouse(houseId) is the one Core entry point — it charges Doggiehood.Core.Expansion.HouseUpgradeNumbers.CostToReach (100/200/400) from Wallet and raises the house's level (House.RaiseLevel), returning false with no state change when the house is unknown, already at HouseUpgradeNumbers.MaxLevel (4), or unaffordable. The decoration cap is GameState.TryAddDecoration (capacity = level); the raw AddDecoration stays uncapped so save-load and grandfathered data are never removed. The player-facing upgrade button ships on the house profile view (#294): its footer Upgrade button calls TryUpgradeHouse directly on tap (Derek's Option A — no confirmation screen), shows the next step's cost, disables into a Max level state at the cap, and greys out when the live wallet can't afford the next step (HouseProfile.CanAffordUpgrade). The mesh-swap is a world re-render on the Unity side (#407): WorldBuilder.BuildHouse picks the mesh by level once, at build time, so raising the level in Core does not by itself grow the already-built HouseView — a v0.6 playtest bug left the world house on its old mesh while only the profile panel advanced. On a successful TryUpgradeHouse the overlay's upgrade wiring now asks HouseUpgradeDirector.RefreshHouse to destroy the stale HouseView and rebuild it through BuildHouse at the new level (the mirror of how ExpansionDirector swaps an empty-lot marker for the real house on build), then re-wires the fresh view's taps to both the profile-open handler and QuestDirector's spray path (via the idempotent QuestDirector.WireHouses) so a rebuilt house stays tappable. Rebuilding from the same Core House/HouseLot preserves a zone house's rolled ladder + palette tint (#299) and a vacant house's greyscale (#58). Because the live quest-delivery flow (QuestManager.DeliverPackage) still uses the uncapped AddDecoration, the capacity cap governs the new TryAddDecoration path only — how a decoration quest behaves against a full yard is a separate, undesigned decision left for when the decoration/upgrade UI is built.

    Expansion indicator (discoverability)¶

    The neighborhood needs a visible signal that it can grow — a marker on the map for an unexplored/expandable zone, tinted so the player can tell at a glance whether they can afford to unlock it right now. Where the unlock action lives is now settled (Derek, 2026-07-28, on #343): the lock icon itself is the affordance (Option A) — tapping an affordable (gold) lock raises the reusable confirmation dialog, and Yes unlocks the zone. The remaining onboarding piece of #178 (how the player first learns coins unlock zones) stays a separate, open discoverability question; this section covers the indicator and its tap.

    Decisions (Derek, on #178): the indicator is a lock icon marking the locked/expandable zone (2026-07-16) — Kenney's locked Game Icon (CC0), staged at Assets/Art/UI/ExpansionIndicator/Resources/locked.png. It hovers just past the end of the road at the entrance to the next locked zone (2026-07-18: "The icon could be hovering just passed the end of the road"), with its position derived from the zone's authored tile layout (#109) rather than hand-placed. It tints gold when the wallet covers the next zone's unlock cost, grey/black otherwise (2026-07-18: "Grey or black lock icon if can't purchase. Gold icon if affordable."), updating live as the balance changes. Since #343 the tint also gates the tap: tapping a gold lock raises the confirmation dialog, a grey/black lock's tap is a no-op — what the tint promises is exactly what the tap does. The one remaining #178 question (onboarding the coins→zones concept) stays open.

    Implementation note (#178, reworked by #453): Doggiehood.Core.Expansion.ExpansionIndicatorPlacement.Resolve(placed, frontierCoordinate) finds which edge of a frontier coordinate already borders the placed TileMap, then returns that edge's midpoint (TileGeometry.EdgeMidpoint) pushed ExpansionIndicatorNumbers.HoverOffset (one WorldDimensions.RoadWidth) further away from the map — "just past the end of the road". Doggiehood.Core.Expansion.ExpansionIndicator.ResolveAll(state) returns one (TileCoordinate, ExpansionIndicatorState) entry per coordinate in GameState.UnlockableFrontier(), each priced/tinted via the #295 pricing path (TileUnlock.Cost vs the live wallet), NOT ZoneUnlock. On the Unity side, ExpansionUnlockDirector (via WorldBuilder.SyncExpansionIndicators) builds and maintains one ExpansionIndicatorView per unlockable frontier coordinate (spawn for a newly-open coordinate, destroy for one that got placed), each re-reading its own live state every frame — the same "never cache" contract the HUD currency chip uses for the wallet — and hiding itself once its coordinate leaves the frontier. This supersedes the retired single fixed marker (ExpansionIndicator.Resolve(state) / ExpansionIndicatorPlacement.Resolve(map, zone)), which is deleted. The staged icon is a literal black silhouette (RGB (0,0,0), shape carried in alpha), which a standard multiply tint can never recolor (black × anything is still black); Doggiehood.Unity.TintedIcon.Recolor instead builds a new texture preserving the source alpha but replacing every pixel's RGB with the target tint (Palette.ExpansionIndicatorAffordableHex / Palette.ExpansionIndicatorLockedHex), and the view swaps between two precomputed sprites rather than re-tinting every frame. The icon's .meta pins isReadable: 1 (Read/Write Enabled) so GetPixels32 can read it at runtime, per Hand-Authoring Unity Serialized Assets.

    Implementation note (#343, reworked by #453) — the tap-to-unlock trigger. The affordability/cost decision is Core: an indicator's ExpansionIndicatorState (from ExpansionIndicator.ResolveAll) carries the flat TileUnlock.Cost and whether the live wallet affords it, the source the dialog reads (the retired ZoneUnlockOffer is deleted). On the Unity side each per-coordinate ExpansionIndicatorView is tappable (IInteractable + a BoxCollider sized to the sprite, toggled off with the renderer so a hidden lock isn't tappable): tapping an affordable lock raises UnlockRequested with its own coordinate, gated by the same live affordability + frontier-membership that tints/shows it — a grey or stale lock's tap does nothing. ExpansionUnlockDirector wires that event to the reusable ConfirmationDialog (built to confirmation-dialog.md, device-safe UGUI via CandyChromeUgui/bundled font, #298/#291) showing that tile's cost on Yes; Yes calls GameState.TryUnlockTile(coordinate), then the newly unlocked tile is rendered as real neighborhood (WorldBuilder.RenderUnlockedTile; see the #373 note below), its empty-lot markers wired to the #57 build path via ExpansionDirector.WireLots, the lock set is reconciled (that coordinate's lock disappears; any newly-open frontier locks appear), and the world is saved — mirroring how #57 wires EmptyLotView → TryBuildHouse. The currency HUD reflects the spend automatically (it reads Wallet.Coins live).

    Implementation note (#373) — the unlocked zone renders as real neighborhood. A v0.6-playtest bug left a newly unlocked zone as bare lot markers floating over void — no grass, no roads — and the camera couldn't pan far enough to reach it. Both gaps are fixed by deriving the world's ground and roads from the live GameState.Map rather than the fixed starting geometry:

    • Ground — the base grass plane now covers the whole map extent (Doggiehood.Core.World.MapExtent.Covering(map), a half-tile beyond the outermost tiles) instead of the fixed 30m starting pad; it stays the single flat Palette.GrassHex plane (#300 (A)), just grown and re-centred (WorldBuilder.ResizeGroundToMap). So every placed tile, including an unlocked zone's, has grass under it.
    • Roads — a tile's road surfaces are derived from its TileCatalog road edges (Doggiehood.Core.World.TileRoadGeometry.SegmentsFor — one straight arm from the tile centre to each road-carrying edge, the #109 geometry), so an unlocked CulDeSacSouth renders its south arm meeting the origin tile's road the same way any authored zone tile would, rather than depending on the hardcoded NeighborhoodLayout.Roads. The starting intersection keeps its existing polished kit-road corridor + crosswalk rendering; the tile-derived path renders the additional (unlocked) tiles' roads.
    • Camera — the pan bounds recompute from the live map extent on unlock (CameraController.RecomputeBoundsFromMap, Core), so Pan/FocusOn can reach the new zone. The initial bounds derive from the same map-based path (the seeded FourWay origin), so there is a single derivation.

    On a confirmed unlock ExpansionUnlockDirector.ConfirmUnlock calls WorldBuilder.RenderUnlockedTile (grow the ground, render the unlocked tile's roads, drop its empty-lot markers) and grows the live CameraRig's bounds; the initial WorldBuilder.Build renders the same ground/roads for any tile a save had already unlocked (RestoreUnlockedTile). Camera auto-focus toward the revealed zone was left out of scope per triage — only that the player can pan there.

    Implementation note (#398) — dogs wander the unlocked tiles. Unlocking a zone doesn't just render it — dogs then explore it. The walk network dogs wander is now derived from the live GameState.Map (MapWalkNetwork, spanning every road-bearing tile) instead of the starting-intersection-only NeighborhoodLayout cache, and GameState.WalkNetwork rebuilds after TryUnlockTile() succeeds. Dogs (DogView/WanderBehavior) bind to that live network via a provider (() => state.WalkNetwork), so already-spawned dogs wander onto the newly unlocked cul-de-sac's sidewalks without being re-spawned. A freshly unlocked zone's lots have no built house yet, so no front walkway attaches to them — but the tile's sidewalks/crosswalks still span it, since those come from the map's roads. (Once a house is built on a lot it does grow a front walkway, #430.) Visually confirming this depends on the zone's roads/ground actually rendering (the #373 note above).

    Vacant house rendering¶

    Decision update (2026-07-16, Derek, on #58): superseded the earlier "for sale sign in the yard" plan. Instead, the whole house mesh renders greyscaled (desaturated) while vacant and returns to its normal tinted color the moment a dog moves in. This needs no new art asset — it's a flat desaturated material color multiplied over the existing house mesh (the same technique already used for dog coat tinting), not a sign object placed in the yard. It removed the dependency on sourcing a "for sale" sign 3D asset, so #154 is closed as no longer needed.

    Vacancy is Core state (House.IsVacant); the greyscale is purely its visual, with no logic of its own — WorldBuilder reads the flag at build time and picks the flat vacancy tint instead of the house's normal HouseStyleTable coloring, in both the City Kit model path and the graybox fallback.
