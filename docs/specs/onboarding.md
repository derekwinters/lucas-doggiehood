# Onboarding

*Epic: [#18](https://github.com/derekwinters/lucas-doggiehood/issues/18)*

The first time the game is opened, the first dog with a speech bubble walks the player through panning/zooming, tapping the speech bubble, and completing one simple quest — teaching the core loop naturally, without a separate tutorial screen. ([#44](https://github.com/derekwinters/lucas-doggiehood/issues/44))

The guidance is presented as a slim **bottom-center coach prompt** (not a top banner) that is layered over live gameplay, never blocks input, advances itself through the four steps as the player performs each real action, and auto-dismisses once the first quest is complete. Its layout — regions, anchors, and named size/margin constants — is the approved wireframe in [UI Wireframes → Onboarding overlay](ui/onboarding-overlay.md) ([#176](https://github.com/derekwinters/lucas-doggiehood/issues/176)). The old graybox top-banner rendering in `OnboardingOverlay` has been replaced by that bottom-center coach prompt, and the prompt now correctly advances on the real pan/zoom/tap interactions and dismisses after the first quest completes ([#207](https://github.com/derekwinters/lucas-doggiehood/issues/207)).

Because this is a kids' game, the two **movement** steps also *show* the gesture: an animated looping directional-arrow coach layers over the map during the **Pan** step (arrows cycling left→right, right→left, up→down, down→up) and the **Zoom** step (a symmetric pair spreading apart to zoom in, closing together to zoom out), then hides the instant the real pan/zoom is registered. The `TapBubble`/`CompleteQuest` steps are unchanged. The beat sequencer is engine-free Core (`GestureCoach`); the thin `OnboardingOverlay` computes each arrow's screen offset and draws it. See [Onboarding overlay → Gesture-arrow coach](ui/onboarding-overlay.md#gesture-arrow-coach-330) ([#330](https://github.com/derekwinters/lucas-doggiehood/issues/330)).

## First-launch quest seeding ([#312](https://github.com/derekwinters/lucas-doggiehood/issues/312))

On the very first launch the world seeds **exactly one** dog with a single easy **lost-item** quest, and the normal hourly-trickle [rotation](quests/economy.md#core-loop) is **suppressed until onboarding completes**. This guarantees the tutorial has one and only one gentle tap-to-find target — the `OnboardingSequence` resolves that seeded dog as its `TargetDog`, so step 4 ("complete a quest") is always the low-friction lost-item tap rather than, say, a purchase or pest-control errand competing for attention.

The branch lives in Core (`QuestManager.BeginInitialQuests(rng)`): with onboarding incomplete it seeds the one lost-item quest and returns; once onboarding is complete it is just the normal `StartNewDay` rotation. The thin Unity layer (`WorldBootstrap`) calls the seam behind its existing "no active quests" guard — no game logic in the `MonoBehaviour`.

When onboarding finishes, its `Done` transition now grants **step 1 of the [onboarding reward-chain](#onboarding-reward-chain-316)** (a 100-coin completion bonus) rather than starting the daily rotation. The normal rotation stays suppressed across the rest of the guided chain and is released only when the chain completes at its final (build) step — at which point the release seeds an **immediate batch** to the population target (up to 5 ready dogs at the starting population), and the recurring hourly rotation ([#310](https://github.com/derekwinters/lucas-doggiehood/issues/310)) then continues from that seeded set ([#579](https://github.com/derekwinters/lucas-doggiehood/issues/579)). ([#316](https://github.com/derekwinters/lucas-doggiehood/issues/316))

## Onboarding reward-chain ([#316](https://github.com/derekwinters/lucas-doggiehood/issues/316))

*Design settled with Derek, review session 2026-07-28.*

Immediately after the first-quest tutorial, a **one-time, first-run scripted reward-chain** walks a new player through every core early mechanic and seeds enough coins that they never stall. It is a fixed four-step sequence — **not** the random rotation — that fires each step **exactly once, in guaranteed order**, paying a flat **100 coins** per step (`OnboardingRewardChainNumbers.RewardPerStep`) by reusing the quest reward-payout path (a wallet deposit):

1. **Complete the first quest** (samples the quest loop) → 100 bonus. Core entry: `GameState.GrantOnboardingCompletionReward`, fired by `OnboardingSequence` when the guided quest completes.
2. **Upgrade a house** (L1 → L2, cost 100) → 100. Core entry: `GameState.TryUpgradeHouse`. **Scoped to the first-quest dog's house** ([#469](https://github.com/derekwinters/lucas-doggiehood/issues/469)): the step advances only when *that* house is upgraded. When the first quest completes, `OnboardingSequence.Complete` hands the target dog's `HouseId` to `GameState.GrantOnboardingCompletionReward`, which records it on `GameState` (persisted via `SaveCodec` alongside `rewardChain=`, so it survives a reload mid-chain). While the chain waits on this step, `TryUpgradeHouse` is a no-op (no charge, no level change) for any other house — this is what stops the self-funding ladder below from soft-locking when the sole 100 coins would otherwise be spent on a house that doesn't advance the chain. The restriction lifts the instant the chain moves past `UpgradeHouse`, so ordinary post-onboarding upgrading of any house is unaffected. The Unity house profile surfaces it through the *existing* disabled-Upgrade-button affordance (a non-target house greys out exactly like an unaffordable one, via `GameState.IsHouseUpgradeEligible`) — no new UI.
3. **Expand the map** (first zone, cost 100) → 100. Core entry: `GameState.TryUnlockNextZone`; the player-facing lock-icon trigger lands with [#343](https://github.com/derekwinters/lucas-doggiehood/issues/343)/[#344](https://github.com/derekwinters/lucas-doggiehood/issues/344).
4. **Build a house** on the newly unlocked lot (cost 50) → 100. Core entry: `GameState.TryBuildHouse`.

**Self-funding ladder.** The 100 bonus covers the 100 upgrade; the upgrade reward covers the 100 expand; the expand reward covers the 50 build; and because the build costs only 50, the player ends the chain with a small cushion. The costs are the shipped v0.4 sink prices — see [Neighborhood Expansion → pricing](expansion.md#pricing) and [Economy → Numbers](quests/economy.md#numbers-placeholder-expect-tuning).

**Ordering and one-time guarantee.** The chain (`OnboardingRewardChain`, engine-free Core) tracks the step it is waiting on. A tracked action taken out of turn — or repeated after it already paid — neither pays nor advances; the chain simply keeps waiting on its current step. Progress round-trips through the save (`SaveCodec`), so the chain resumes where it left off and is never restarted or re-paid on reload; a pre-#316 save that had already finished onboarding is treated as a completed chain.

**Rotation handoff (#312 → #310, seeded release #579).** The normal quest rotation stays suppressed while the chain is in progress and is released **exactly when step 4 (build) completes** — no rotation is seeded mid-chain. The release is an **immediate batch seed**, not a single hourly tick: `ReleaseInitialRotation` requests the full `TargetActiveCount` in one shot (skipping the per-hour accumulator throttle for this one event), so the player finishes onboarding to a populated board of up to 5 ready dogs on distinct houses rather than a near-empty board that would trickle up over the following hours (at the starting 1.25/hr rate the first hourly tick adds only `floor(1.25)` = 1 — the [#579](https://github.com/derekwinters/lucas-doggiehood/issues/579) halt). The headroom cap, free-dog cap, and ≥1-free-quest guarantee still apply to the seed; the accumulator and rotation clock are left untouched, so the recurring #310/#543 pacing then continues the normal hourly trickle cleanly from that seeded set. The single Core decision `QuestManager.EnsureQuestsForLaunch` applies this at every launch (pre-chain seed → mid-chain suppression → post-chain refresh), so the thin Unity bootstrap carries no pacing logic.

**Guided by the same coach bar (#371).** The one standard onboarding [coach bar](ui/onboarding-overlay.md#standard-onboarding-coverage-374) ([#374](https://github.com/derekwinters/lucas-doggiehood/issues/374)) guides each reward-chain step, not just the first quest: after the first quest it re-shows for **upgrade a house → expand the map → build a house**, advancing as each real action completes on `RewardChain`, then dismisses for good when the chain completes. The coach bar names the current onboarding **phase** with a top-left gold [phase-title tab](ui/onboarding-overlay.md#phase-title-region) — "Learn the ropes" through the tutorial, then "Fix up a home" / "Grow the neighborhood" / "Build a house" for the three reward-chain phases — swapping once per phase, not per step; it carries no step-count indicator ([#435](https://github.com/derekwinters/lucas-doggiehood/issues/435)). The per-step prompt copy, the per-phase title lookup, and the "keep showing until the chain completes" dismissal gate are engine-free Core (`OnboardingCoach`); the coach-bar layout is the approved wireframe.

**Target-house highlight on the upgrade step ([#571](https://github.com/derekwinters/lucas-doggiehood/issues/571)).** While the chain waits on **step 2 (upgrade a house)**, the target house — the first-quest dog's house, above — is marked with the *existing* red ground-ring highlight (the reduced lost-item finder glow, [#535](https://github.com/derekwinters/lucas-doggiehood/issues/535)) so it is obvious which house to tap and upgrade. This reuses the game's established red target-highlight vocabulary rather than inventing a new cue, and it fills the exact gap left by [#506](https://github.com/derekwinters/lucas-doggiehood/issues/506): the coach bar is suppressed while a centered profile panel is open, so the "tap this house, then Upgrade…" reminder vanishes precisely when the house profile is open — the persistent ring keeps the "this one" cue visible before the panel opens and, unlike the bottom coach bar, does not collide with the centered panel (so it is deliberately **not** gated by the coach-bar suppression). The show/target decision is engine-free Core (`OnboardingHouseHighlight`, reading only `RewardChain.CurrentStep` and the recorded `GameState.OnboardingUpgradeTargetHouseId` — no new state); the thin Unity view (`OnboardingHouseHighlightDirector`/`OnboardingHouseHighlightView`) attaches the flat, non-pulsing, collider-free ring to *exactly* the target house and tears it down the instant the chain advances past `UpgradeHouse` (the house is upgraded, or a reload already past it). Like the finder glow, the highlight is a **ring outline** (a hollow annulus), not a filled disc — it frames the house rather than painting a patch over the ground inside it, sharing the same `GroundRingMesh` so both red target highlights stay visually consistent ([#602](https://github.com/derekwinters/lucas-doggiehood/issues/602)). The ring's footprint is sized from the target house's own renderer bounds (like the bug-swarm marker), not the fixed lost-item ring scale, so it reads correctly under any house variant/level.

**Invariant — a target ring's inner edge always lies outside the target's footprint, with a non-zero gap** ([#669](https://github.com/derekwinters/lucas-doggiehood/issues/669)). The ring frames the house; the house never sits over the ring. Concretely: the whole XZ footprint, **corners included**, lies inside the ring's **hole**, with a visible band of open ground between the mesh and the ring's inner edge — and the ring is **concentric with the house's mesh**, not its transform pivot. Two things make that easy to get wrong, and both were wrong before #669. A circle has to clear the footprint's **diagonal**, not its longest side — a square house of side `w` reaches `1.414·w` corner to corner, so *any* "multiply the longest side" rule below `√2` covers the ring by construction, no matter how it is tuned. And because the band is hollow, the edge that has to clear the house is the **inner** one, so the gap is applied against the hole rather than the outer edge. The rule is one engine-free Core type (`TargetRingGeometry`) with a single named gap constant, shared by every target ring — the build-step foundation highlight ([#668](https://github.com/derekwinters/lucas-doggiehood/issues/668)) inherits it rather than growing its own numbers — and it reads the annulus's hole ratio from the one shared constant, so a change to that hole can't silently break containment. The gap is bounded above as well as below: containing the footprint through a hole opens the ring to roughly twice the target's diagonal, so a max-level house's ring nearly fills its lot, and the ring must still stay **inside the marked house's own lot** so it can never read as pointing at a neighbour.

> **How the spec is changing (#669).** It used to say only that the ring is "sized from the target house's own renderer bounds… so it reads correctly under any house variant/level" → it now also says *how* those bounds become a size: the footprint's diagonal must fit inside the ring's hole with a gap, concentric with the mesh → because the old wording was fully satisfied by a ring the house completely covered. The shipped rule really did derive its size from the bounds — from `1.15 × the longest side` — which for a square house put the ring's outer edge ~19% inside the house's own corners, so it showed as a couple of red slivers rather than a ring. Stating containment as an invariant makes "sized from the bounds" mean something a wrong implementation can fail.

**Celebrated by a toast (#562, supersedes the #372/#374 modal panel).** Each step's payout is no longer silent: when a reward-chain step actually pays out, a non-modal [toast notification](ui/toast.md) slides into the reserved top-left HUD lane — a cream pill with a gold coin token and a single line carrying the per-step accomplishment plus the payout (e.g. **"You finished your first quest! +100 coins"**) — then clears itself on a short auto-timeout or the moment it is tapped (always dismissible, cf. [#329](https://github.com/derekwinters/lucas-doggiehood/issues/329)). This **reverses** the earlier decision ([#374](https://github.com/derekwinters/lucas-doggiehood/issues/374)) to celebrate each step with the modal [onboarding reward panel](ui/onboarding-reward.md) — that "brief blocking-modal celebration beat" exception is withdrawn, so onboarding now raises **no** blocking modal on a reward-chain step; the celebration is a lightweight HUD toast that never interrupts play. The per-step copy is unchanged, carried over verbatim onto the toast. The plumbing keeps the Core/Unity split: `OnboardingRewardChain` raises a `RewardGranted` event carrying only the just-completed step + amount (no copy in Core), and the thin Unity layer maps the step to its approved message and shows the toast. The payout itself is unchanged — the toast is pure presentation over the existing `Wallet.Deposit`, and the currency chip updates on its own; a reloaded chain never re-pays nor re-celebrates.

## Step-gated speech bubble & self-heal ([#329](https://github.com/derekwinters/lucas-doggiehood/issues/329))

The four steps run in order — `Pan → Zoom → TapBubble → CompleteQuest → Done` — and the "tap the speech bubble" action is gated to its own step so each step is the obvious next thing to do:

- **The target dog's speech bubble is hidden until the `TapBubble` step.** While onboarding is running, the seeded dog's bubble does not appear (and cannot be tapped) during `Pan`/`Zoom`; it becomes visible and tappable for the first time exactly when the flow reaches `TapBubble`. The gating decision lives in Core (`OnboardingSequence.ShouldSuppressBubble`); the thin Unity layer (`DogView` via `OnboardingOverlay.SuppressesBubbleFor`) just consults it. Only the target dog is gated — other dogs are unaffected (and during the single-seeded onboarding, #312, there are none). Once onboarding is complete, bubbles follow their normal `HasActiveQuest` binding.
- **The `TapBubble` step self-heals if the interaction already happened.** Should the conversation somehow have been opened early (or the quest already accepted/resolved before the step), the sequence does not strand. `OnboardingSequence` remembers that the target dog's conversation was opened even if it fired before `TapBubble`, and on entering `TapBubble` — or on any overlay poll (`OnboardingSequence.Reconcile`) — it auto-advances when the conversation was already opened or the target dog's quest is no longer `Available`, cascading on through `CompleteQuest`/`Done` when the quest is already fully resolved. This closes the soft-lock where an early bubble tap left the coach bar pinned on `TapBubble` forever.
- **The conversation dialog is always dismissible.** The "Not now" decline ([#185](https://github.com/derekwinters/lucas-doggiehood/issues/185)) stays reachable in every onboarding state, so no path leaves the dialog stuck open.

## Build checklist

- [ ] First-launch state is tracked (so onboarding only runs once)
- [ ] Guided prompts cover: panning, zooming, tapping a speech bubble, and completing a quest through to reward
- [ ] Onboarding uses the real game systems (an actual dog, actual quest, actual reward) rather than a separate scripted tutorial scene
- [ ] No blocking modal tutorial screen — guidance is layered over live gameplay
- [ ] The upgrade-step target-house ring **contains** the house: the whole XZ footprint, corners included, sits inside the ring's hole with a visible gap of open ground, concentric with the house's mesh (not its pivot), and still inside that house's own lot at max upgrade level ([#669](https://github.com/derekwinters/lucas-doggiehood/issues/669))
