# World & Neighborhood

*Epic: [#2](https://github.com/derekwinters/lucas-doggiehood/issues/2)*

## Starting scope

The first playable neighborhood is deliberately small: **one intersection of two streets, with one house in each of the four quadrants.** ([#38](https://github.com/derekwinters/lucas-doggiehood/issues/38))

- 4 houses total to start, each home to a dog household (see [Dog Roster & Names](../dogs/roster-names.md))
- More streets and houses are designed and slated for **v0.4** — see [Neighborhood Expansion](../expansion.md)

## Layout

Streets are lined with houses that the player views and explores from above ([#7](https://github.com/derekwinters/lucas-doggiehood/issues/7)). There is no player-character traversal — see [Camera, Navigation & Controls](camera-controls.md) for how the player actually moves through the space.

## House scale

> **Decision (2026-07-14, Derek, on [#145](https://github.com/derekwinters/lucas-doggiehood/issues/145)):** every City Kit Suburban house model renders at **one fixed uniform scale: ×7** — the kit-wide default unless a specific model gets a documented exception (none today). This replaces the earlier rule that normalized each model's max horizontal footprint to a uniform 8m, which gave every model a *different* scale factor — houses weren't actually at the same scale, so doors read different sizes house to house.

The constant lives in Core as `HousePlacement.KitScale` (`WorldBuilder.HouseKitScale` is the Unity-side alias), and everything downstream — front-setback placement, door world positions, walkway starts, the catalog gallery — derives from it. At ×7 the four starting models' footprints are: building-type-b **12.80×7.98m**, building-type-g **10.15×8.25m**, building-type-k **6.45×7.14m**, building-type-m **10.00×10.00m**. ×8 was rejected at the time because building-type-b would have been 14.6m wide against [#129](https://github.com/derekwinters/lucas-doggiehood/issues/129)'s then-current 15m lot-fence square (a 0.5m-margin guard); at ×7 it kept a 1.1m margin. That square is gone — fences were reshaped to house-anchored backyard runs ([#146](https://github.com/derekwinters/lucas-doggiehood/issues/146)) and then widened to trace the lot boundary ([#342](https://github.com/derekwinters/lucas-doggiehood/issues/342), see [Backyard fences](#backyard-fences)) — but the ×7 decision stands on its own.

## Property bounds

> **Decision (2026-07-20, Derek, on [#222](https://github.com/derekwinters/lucas-doggiehood/issues/222)):** a **property (lot) is one quadrant of a tile**. On the starting FourWay intersection each of the 4 quadrants is a property; that same quadrant size is the standard for every layout — tighter layouts (the deferred [tile catalog](tile-catalog.md#the-17-tile-types)) simply fit fewer properties, never a differently-sized one.

The geometry lives in Core (`LotBounds`): `QuadrantBounds(lot)` returns a rectangle sized to one tile-quadrant (half the 60m `WorldDimensions.TileSize` per side, so 30m×30m) positioned on the lot's own `HouseLot.Quadrant` — **not** on `HouseLot.Position` (the separate, hand-picked ±14m house-placement anchor described above). Sizing a full tile-quadrant box around that 14m anchor would overlap the opposite lot's bounds across the road by a meter; centering each quadrant on the tile's own N/S/E/W split instead makes the 4 starting lots' bounds exactly tile the 60m tile with no gap or overlap between neighbours.

`LotBounds.FrontYard`/`BackYard` split those bounds relative to `HousePlacement.FrontFacing`, excluding the house footprint — the front yard is the portion between the house's front facade and the yard/pavement line, the back yard the portion between the house's rear wall and the lot's far edge, both spanning the lot's full width. Because a quadrant's bounds tile the whole 60m tile with no gap, the front yard's raw street-side edge sits *on* the tile centerline where the faced road runs; `FrontYard` therefore pulls that edge inward by `LotBounds.StreetCorridorInset` (the road half-width + grass verge + sidewalk width = the sidewalk's outer edge, the same 5.75m boundary house facades set back from, all derived from `WorldDimensions`) so the region ends where the actual yard begins and never overlaps the road or sidewalk ([#244](https://github.com/derekwinters/lucas-doggiehood/issues/244)).

But on the FourWay every quadrant borders **two** roads — one on each of its inner edges (the tile-centerline edges at X=0 and Z=0) — and #244 only trimmed the **faced** road, so both yard regions still spanned onto the **perpendicular** road's centerline and trees landed in it ([#272](https://github.com/derekwinters/lucas-doggiehood/issues/272)). `LotBounds.ClearRoadCorridors` closes that: after the facing split, it pulls *every* yard edge that lies on a road centerline inward by the same `StreetCorridorInset`, for **both** the front and back regions. Which edges border a road is derived generically from `NeighborhoodLayout.Roads` — an edge is trimmed only when it lies on a road's centerline *and* overlaps that road's finite extent — so the rule survives map expansion rather than hard-coding the two inner quadrant edges, and an edge #244 already inset (a full `StreetCorridorInset` off the centerline) is left untouched, so the two trims compose without double-insetting. This is the region [Yard landscaping](#yard-landscaping) scatters trees into.

## Backyard fences

> **Decision (2026-07-28, Derek, on [#342](https://github.com/derekwinters/lucas-doggiehood/issues/342) adopting [#147](https://github.com/derekwinters/lucas-doggiehood/issues/147)'s settled geometry, superseding the [#146](https://github.com/derekwinters/lucas-doggiehood/issues/146)/[#129](https://github.com/derekwinters/lucas-doggiehood/issues/129) house-width fence):** the backyard fence traces the **lot boundary**, not the house. The fence line is inset from **every** edge of the lot's quadrant bounds by one **sidewalk width** (2m) — uniform whether that edge borders a sidewalk, a neighbouring yard, or the map edge, so the old corner-lot special-casing dissolves. The shape is **five runs, front open**: two side runs + one rear run trace the offset boundary rectangle around the back yard, and two short connectors turn perpendicular-inward from each side run's front end (at the house's depth midpoint) to the house **side-wall midpoints**. The **front yard stays open** — no fence line crosses the front, so the front walkway ([#128](https://github.com/derekwinters/lucas-doggiehood/issues/128)) runs door → sidewalk through the open front and never meets a fence. Fences are **defined for every lot but hidden by default** — a future fence-purchase quest purchases them ([#147](https://github.com/derekwinters/lucas-doggiehood/issues/147)/[#318](https://github.com/derekwinters/lucas-doggiehood/issues/318)).

The geometry lives in Core (`LotFence`): `GeometryFor` traces the lot's actual `LotBounds.QuadrantBounds` ([#222](https://github.com/derekwinters/lucas-doggiehood/issues/222)) inset by `LotFence.BoundaryOffset` (= `WorldDimensions.SidewalkWidth`, 2m) on every edge, and emits five runs that rotate with the house facing (a house facing +X has its side walls along Z): connector → side run → rear run → side run → connector. Because the offset is uniform on every edge, the enclosed back yard is now the **full lot width** — 26m across a 30m quadrant — rather than the house footprint (the widening [#342](https://github.com/derekwinters/lucas-doggiehood/issues/342) delivers). The rear run traces the offset boundary near the quadrant's far edge, retiring #146's shallow 7.5m house-anchored rear line. The two short connectors keep the front open by reaching in only at the house's depth midpoint. The lot-free catalog-gallery form ([#126](https://github.com/derekwinters/lucas-doggiehood/issues/126)) applies the same offset against a **standard quadrant** (`WorldDimensions.TileSize`/2 per side, identical for every lot) synthesised around the house, so the gallery shows the real offset outline without a per-model boundary. Because the quadrant edges sit on the tile centrelines, a side run on a road-bordering edge lands one sidewalk width off that centreline — validated in the Editor via `WorldBuilder.ForceFencesVisible` ([#152](https://github.com/derekwinters/lucas-doggiehood/issues/152)).

Fencing is **per lot** — `HouseLot.HasFence`, default **off** since #146 — so the built world renders **no fences** today. The geometry stays queryable for a disabled lot: `LotFence.GeometryFor` always describes the fence (the #147 purchase flow and the [#126](https://github.com/derekwinters/lucas-doggiehood/issues/126) gallery need it), while the flag-respecting `LotFence.RunsFor` — empty while hidden — is what `WorldBuilder` consumes. `WorldBuilder.ForceFencesVisible` is the Editor-check/test seam that builds every fence anyway.

Visually, fences render as tiled Kenney City Kit Suburban `fence` pieces at uniform scale ×5 (1.35m tall — half the ground-tile scale, which would read as a 2.7m wall). Core's `FenceTiling` compresses a whole number of pieces to cover each run exactly (the same compress-to-fit rule as the walkway pavers), so fence ends land precisely on the side-wall connector ends and the offset boundary corners; `WorldBuilder` instantiates the pieces verbatim and falls back to one thin graybox rail per run when the kit piece can't be loaded. The catalog gallery shows each model's real backyard fence outline from the same Core API (`LotFence.BackyardRuns`).

## Yard landscaping

> **Decision (2026-07-20, Derek, on [#222](https://github.com/derekwinters/lucas-doggiehood/issues/222)'s conversation, reworked into [#170](https://github.com/derekwinters/lucas-doggiehood/issues/170)):** yards get low-poly trees/plants placed **procedurally** — zero per-lot manual authoring, so the whole neighborhood stays agent-buildable and CI-verifiable. Per property: the **front yard** generates **4** candidate points and shows **1** most of the time, **2** occasionally; the **back yard** generates **11** candidates and shows **3-5**. Selection is **seeded/deterministic per lot** — the same lot always lands on the same trees across sessions and builds.

The geometry lives in Core (`YardLandscaping`), split the same two-tier way as `LotFence`: pure `GenerateFrontCandidates`/`GenerateBackCandidates`/`SelectFront`/`SelectBack` overloads take explicit yard regions and obstacles, while the `*For(HouseLot)` overloads resolve that geometry from `NeighborhoodLayout`/`LotFence` and derive the seed from the lot's own `HouseLot.HouseId`. Candidates are rejection-sampled inside [Property bounds](#property-bounds)' `LotBounds.FrontYard`/`BackYard`, collision-aware against the house footprint, the front walkway ([#128](https://github.com/derekwinters/lucas-doggiehood/issues/128)), the backyard fence line (checked via `LotFence.GeometryFor`, regardless of whether the fence is currently purchased/visible), and each other. Candidates additionally stay clear of **every** road bordering the lot — faced *and* perpendicular — because the yard regions themselves now end at the paved street corridor (`LotBounds.StreetCorridorInset`) on every road-bordering edge rather than reaching the tile centerline. Playtesting ([#244](https://github.com/derekwinters/lucas-doggiehood/issues/244)) first showed front trees escaping into the *faced* road; a follow-up ([#272](https://github.com/derekwinters/lucas-doggiehood/issues/272)) showed they still landed in the *perpendicular* side road, since a quadrant borders two roads and #244 trimmed only the faced one — `LotBounds.ClearRoadCorridors` (see [Property bounds](#property-bounds)) now trims both, for the front and back regions alike, so a candidate's full scaled footprint clears every road it borders. Every candidate and pick is spaced by `YardLandscaping.MinSpacing`, two footprint radii derived from the larger canopy half-extent of the two kit tree meshes (tree-large.fbx/tree-small.fbx, which share a canopy footprint) at the module's uniform scale, so no placed prop can ever overlap another regardless of which model lands where.

> **Decision (2026-07-23, Derek, on [#243](https://github.com/derekwinters/lucas-doggiehood/issues/243)):** the earlier `planter` kind is **removed entirely** — playtesting showed planters placed in odd, random yard spots, so the whole code path is gone and a planter can never be selected or rendered. Only the two tree meshes remain; the collision spacing (previously keyed off the planter, the widest piece) is re-derived from the larger tree canopy half-extent.

Visually, each pick instantiates its selected `tree-large`/`tree-small` Kenney City Kit Suburban model at uniform scale ×5 (matching `FenceTiling.Scale`, since the trees stand alongside the same backyard fences — Derek tunes both further in the Editor check). `WorldBuilder` builds one "Yard - N" container per lot holding its front-then-back picks, falling back to one simple primitive marker per pick (same pattern as the walkways/fences) when a kit piece can't be loaded.

## Lighting & time

Static, pleasant daytime lighting — always sunny/mid-day. **No day/night cycle and no weather system for v1.0.** ([#39](https://github.com/derekwinters/lucas-doggiehood/issues/39))

This is a deliberate simplification: it avoids needing lighting variants for every asset, and a future weather/day-night system is tracked separately as an explicit future idea — see [Future Ideas](../future-ideas.md).

## Art direction

Low-poly 3D art style throughout — houses, dogs, streets, and props all share this style ([#6](https://github.com/derekwinters/lucas-doggiehood/issues/6)). The specific color palette and house architecture are specified in [Art & UI Style](art-style.md).

A cover art concept for the game exists at [#90](https://github.com/derekwinters/lucas-doggiehood/issues/90) as a visual reference for overall tone.
