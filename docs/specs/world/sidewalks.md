# Sidewalks & Walk Network

*Related: [#106](https://github.com/derekwinters/lucas-doggiehood/issues/106) (this page), [#105](https://github.com/derekwinters/lucas-doggiehood/issues/105) (locked world dimensions this page consumes), [#128](https://github.com/derekwinters/lucas-doggiehood/issues/128) (front walkways, which replaced the driveway stubs on this page), [#109](https://github.com/derekwinters/lucas-doggiehood/issues/109) (multi-tile grid the walk network now derives its roads from, via [#398](https://github.com/derekwinters/lucas-doggiehood/issues/398)), [#112](https://github.com/derekwinters/lucas-doggiehood/issues/112) (approach-to-rest movement, which routes dogs to their comfort decorations over this network)*

## Symmetric sidewalk placement

Every road gets a sidewalk on **both** sides — not just one edge. Moving outward from the road centerline: road → verge setback → sidewalk, mirrored on the other side, with grass outside the sidewalk. The widths are the locked [standard dimensions](tile-catalog.md#standard-dimensions) (`WorldDimensions`, [#105](https://github.com/derekwinters/lucas-doggiehood/issues/105)) — nothing on this page introduces a new measurement:

| Standard | Value |
|---|---|
| Road width | 6m |
| Grass verge (road edge → sidewalk) | 0.75m — a logical setback, see below |
| Sidewalk width | 2m |

> **Decision (2026-07-13, Derek, in conversation):** the grass verge between road and sidewalk no longer exists — `GrassVergeWidth` went from `1.5m` to `0m`. This supersedes the original [#106](https://github.com/derekwinters/lucas-doggiehood/issues/106) verge. Context: aligning Core's walk geometry with the Kenney City Kit Roads art ([#121](https://github.com/derekwinters/lucas-doggiehood/issues/121)/[#122](https://github.com/derekwinters/lucas-doggiehood/issues/122)). At tile scale 10, a kit road tile has road surface 0–3m from the centerline and a raised curb+sidewalk band spanning 3–5m; with a 0m verge, Core's sidewalk centerline lands at exactly 4m — dogs walk centered on the kit's modeled pavement, and the crosswalk edges (±4m) land inside the crossroad tile's own corner sidewalks (4–5m). The constant stays in `WorldDimensions` (and in the offset formula) so the geometry keeps deriving from one place.

> **Decision (2026-07-13, Derek, in conversation — follow-up to the above, same day):** `GrassVergeWidth` is now `0.75m`. After seeing the kit world in the Editor, Derek found the dogs at 4m "a little too close to the road" and asked for the midpoint between the previous distance (5.5m at the 1.5m verge) and the current one (4m at the 0m verge) — putting the dogs' walk line at `4.75m`. This is a **logical setback for dog placement**, not a return of the visual grass strip: the kit tiles pave 3–5m from the centerline, so in the kit-art path nothing visually changes and the earlier "no grass verge" decision (a visual call) stands — 4.75m sits within the paved band, near its outer edge. Only `WorldBuilder`'s primitive graybox fallback renders the 0.75m verge as an actual grass strip.

A sidewalk's centerline sits `RoadWidth / 2 + GrassVergeWidth + SidewalkWidth / 2` from the road's own centerline — `4.75m` for the starting intersection's two roads. `Road` and `Sidewalk` (Core, `Assets/Scripts/Core/World/`) express this purely as that formula over `WorldDimensions`; a guard test (`WorldDimensionsGuardTests`) fails the build if any of the locked values is ever re-declared as a literal outside `WorldDimensions.cs`.

## Road arm extent

Each of the starting intersection's two roads (and, keying off the same extent, each road's two sidewalks) runs a fixed distance either way from the origin — `NeighborhoodLayout.StreetHalfLength`. That extent is **half a tile** (`WorldDimensions.TileSize / 2` = 30m), so every arm reaches the **tile edge**. The `WalkNetwork` sidewalk arms and everything else derive from `NeighborhoodLayout.Roads`, so lengthening the arms extends the walkable sidewalks with them.

> **Decision (2026-07-31, Derek, on [#392](https://github.com/derekwinters/lucas-doggiehood/issues/392)):** the road arms **extend the full distance to the tile edge**. Previously `StreetHalfLength` was a hand-picked `26m` — 4m short of the tile edge — so once the `#147` backyard fences traced the lot quadrants nearly to the tile edge, a green band showed between each road arm's end and the edge, and on expansion two adjacent tiles' arms would leave an ~8m green gap instead of a continuous street. `StreetHalfLength` is now **derived** from `WorldDimensions.TileSize / 2` (30m) — the same tile-edge convention the generic multi-tile system already uses (`TileGeometry.EdgeMidpoint`, `LotBounds.QuadrantBounds`) — so adjacent tiles' roads meet edge-to-edge and read as one connected street network. In the kit-art path, the visual road corridor tiles each arm with a whole number of City Kit road pieces **compressed evenly to span exactly from the intersection tile's edge (5m) to the tile edge (30m)** — the same compress-to-fit technique as the front-walkway pavers ([#128](https://github.com/derekwinters/lucas-doggiehood/issues/128), `WalkwayTiling.PiecesAlong`), scaling only the along-road axis so the road-band width and texture don't distort and no untiled sliver is left at the edge.

## The crosswalk box

At the starting intersection, the two crossing roads produce four box corners (one per compass direction the roads' sidewalks meet). Each of the 4 road arms — N, S, E, W — gets one crosswalk, `CrosswalkWidth` (3m) wide, connecting the two box corners on either side of that arm and letting a pedestrian cross straight over that road instead of going the long way around through both corners. A **three-way (Tee) intersection** gets **one crosswalk per real arm — three, not four** — with no crosswalk over its closed (roadless) edge.

Crosswalk rendering is derived **per tile from the tile catalog geometry** (`TileCrosswalkGeometry.RectanglesFor`, [#508](https://github.com/derekwinters/lucas-doggiehood/issues/508)) — one patch per road-bearing edge of every intersection tile — so **every unlocked intersection paints correct crosswalks, not just the hardcoded origin**. (Before #508, both the kit crossing-tile placement and the primitive fallback read only the static origin `NeighborhoodLayout.WalkNetwork`, so an unlocked Tee rendered no crosswalks at all.) Only true crossings carry crosswalks: the 4-way and the four Tees. A straight, turn, or cul-de-sac tile has no crossing to paint.

In the shipping kit-art path, literal zebra-stripe crosswalks are **baked into the Kenney City Kit Roads intersection mesh** placed at the tile centre — `road-crossroad-path` for a 4-way, `road-intersection-path` for a Tee (its stripes on the three roaded arms only). `WorldBuilder` places the single mesh matching the tile's `TileType`, yawed per `RoadTileArt` (see [Tile Catalog](tile-catalog.md)), so no separate crossing tiles are needed. Only `WorldBuilder`'s primitive graybox fallback (when the kit tiles can't load) renders each crosswalk as a flat, distinctly colored rectangular patch with no markings, one per arm derived from the same per-tile geometry — see [Art & UI Style](art-style.md) for the fallback palette and [Build checklist](#build-checklist) below for what's actually implemented.

A crosswalk is also a **right-of-way** point: a vehicle and a dog never occupy the same point on it, resolved by first-come yielding rather than driving through ([#546](https://github.com/derekwinters/lucas-doggiehood/issues/546)). The claim is keyed on the crosswalk's `WalkEdge` (Core `RoadCrossingGate`), so it is per crosswalk segment and generalizes across every unlocked intersection and every current/future vehicle. A yielding vehicle stops far enough back that its **whole body** stays off the band — the stop is measured at its front bumper, not its centre ([#639](https://github.com/derekwinters/lucas-doggiehood/issues/639)) — so the 3m painted band is never shared. See [Dog Behavior § Yielding at road crossings](../dogs/behavior.md#yielding-at-road-crossings) for the full rule.

Visually, each crosswalk only covers the road and verge band — `RoadWidth + 2 × GrassVergeWidth` (7.5m at the 0.75m verge) — never the sidewalks themselves, which keep their own sidewalk-colored surface right up to the crosswalk's edge. The walk network's `Crosswalk` edge is still a straight line from one sidewalk's center to the other's (that's the real distance a dog covers crossing the road, and it's what keeps the graph connected to the sidewalk arm nodes) — this is purely a rendering clip in `WorldBuilder`, not a change to the graph.

## The walk network graph

`WalkNetwork` (Core) is a generic, data-driven graph over nodes (points) and edges — sidewalk segments, crosswalks, and front walkways — built from whatever `Road`s and house lots are passed to `WalkNetwork.BuildFrom`. The `Road`s are now derived from the live multi-tile map (`MapWalkNetwork.RoadsFrom(TileMap)`, [#398](https://github.com/derekwinters/lucas-doggiehood/issues/398)): every road-bearing tile in `GameState.Map` (the [#109](https://github.com/derekwinters/lucas-doggiehood/issues/109) grid) contributes its road segments from the [Tile Catalog](tile-catalog.md), so the graph spans **every unlocked tile**, not just the starting intersection. Per axis, a tile carrying a road on both of that axis's edges emits one full road through the tile centre (a `FourWay` emits both, exactly reproducing `NeighborhoodLayout.Roads`); a tile carrying a road on only one edge (a cul-de-sac / turn / tee stem) emits a half-length stub from the tile centre out to that edge.

> **Decision (2026-08-05, Derek, on [#581](https://github.com/derekwinters/lucas-doggiehood/issues/581)):** the walk network now **curves at plain `Turn*` bends and cul-de-sac bulb turnarounds to follow the rounded road art**, superseding this page's earlier "the rendered curve of a turn or cul-de-sac is independent of the graph edge" framing for those two cases. A playtest (v0.11) found dogs cutting a straight chord across a bend instead of following the curve. The fix inserts arc waypoints into the graph (see *Curved corners* below). **Explicitly still straight:** `FourWay`/`Tee` box-corner intersection turns stay hard 90° (their crosswalk box is unchanged) — only mid-tile road bends and cul-de-sac turnarounds curve. (The `OpposingTurnsNS`/`OpposingTurnsEW` twin bends were left out of scope here and then removed from the catalog entirely by [#583](https://github.com/derekwinters/lucas-doggiehood/issues/583).)

> **Decision (2026-07-14, Derek, on [#128](https://github.com/derekwinters/lucas-doggiehood/issues/128)):** the neighborhood has **no driveways** — front walkways *replaced* the `DrivewayStub` edges (`WalkEdgeKind.FrontWalkway`; the enum member was renamed, not duplicated) as each lot's connection to the sidewalk. A walkway runs from the house's actual **front door** — the [#125](https://github.com/derekwinters/lucas-doggiehood/issues/125) catalog door position at the [#127](https://github.com/derekwinters/lucas-doggiehood/issues/127) front-setback house position — perpendicular to the street onto the sidewalk, so dogs path to real front doors. It keeps the stub's two contracts: general wander never enters it, and it is the only way on/off a lot. The lot-side node of the connection is therefore the **door**, not the lot center; house lot centers (±14) remain as data anchoring the deferred expansion geometry, but no walk-network edge touches them anymore.

Construction, generically:

1. **Sidewalk arms.** Every road's two sidewalks are split into arms wherever another road crosses them, so a sidewalk never runs through another road's own footprint. At a plain `Turn*` bend the two arms are clipped back `RoadBendCornerRadius` from the shared corner, where the curved arc takes over (step 4).
2. **Crosswalks.** At each **real crossing**, the four box-corner nodes are connected pairwise into the 4-crosswalk box described above. A `Turn*` bend is *not* a real crossing — it emits no crosswalk box (see step 4).
3. **Front walkways.** Each house lot gets one walkway edge from its front door to its street-facing sidewalk.
4. **Curved corners ([#581](https://github.com/derekwinters/lucas-doggiehood/issues/581)).** `MapWalkNetwork.RoadsFrom` emits a plain `Turn*` tile's bend as two independent perpendicular stub `Road`s meeting only at their shared tile-centre endpoint. `WalkNetwork.BuildFrom` distinguishes such a **bend** (the crossing sits at the *end* of both stubs) from a real crossing (interior to at least one road, e.g. a `FourWay`/`Tee`) and, instead of the straight box-corner connection, inserts arc waypoints along two quarter-circle arcs concentric with the road's own corner arc — inner (`RoadBendCornerRadius − ` sidewalk offset) and outer (`+` offset) — so `FindPath` traces the curve. A **cul-de-sac's bulb turnaround** is curved the same way: its two sidewalk arm ends are joined by an arc of radius `CulDeSacBulbRadius` (9m) bulging around the closed bulb. Each inserted arc is subdivided finely enough to read as a smooth curve **regardless of radius** ([#598](https://github.com/derekwinters/lucas-doggiehood/issues/598)): the waypoint count is bounded by both a max angular step *and* a max world-space chord length (`SidewalkWidth`, 2m), so no single hop exceeds that chord. A fixed angular step alone was radius-blind — the large-radius 9m bulb got only ~3 long (~3.3m) chords and read as an angular octagon (a v0.11 playtest finding, follow-up to #581); the chord-length cap forces the big arc into many short hops so the polyline hugs the true curve. Because a dead-end bulb can't be told from a road running to the map frontier by road geometry alone, `MapWalkNetwork` passes the cul-de-sac turnarounds (one per single-road-edge tile) to `WalkNetwork.BuildFrom` explicitly, where the tile type is known; bends are detected geometrically from the roads. The inserted arc endpoints are the existing arm nodes, so the graph stays fully connected. The sidewalk edge nearest the *lot center* still decides which street the house faces (unchanged from the stub, and still what `HousePlacement.FrontFacing` keys off); from that facing, `WalkNetwork.BuildFrom` derives the house's front-setback position (`HousePlacement`'s pure helpers) and its catalog door (`HouseModel.FrontDoorWorldPosition`), then projects the door perpendicularly onto that sidewalk (clamped to the segment) — splitting the sidewalk edge at the attach point if needed. The per-lot edge is queryable via `WalkNetwork.TryGetFrontWalkway(houseId)` (A = door node, B = sidewalk attach).

`GameState.WalkNetwork` is the live network dogs actually wander ([#398](https://github.com/derekwinters/lucas-doggiehood/issues/398)): it is built (lazily, then cached) from the whole unlocked `Map` plus the lots of every **built** house, and rebuilt whenever the map or houses change — after a successful `TryUnlockNextZone()` or `TryBuildHouse()` (and on save-restore). A lot joins the graph (grows a front walkway) once its house has a **resolved model to derive the door from** — either an authored `HouseStyleTable` style ([#64](https://github.com/derekwinters/lucas-doggiehood/issues/64)) *or* a zone-built house's rolled `HouseVariant` ([#299](https://github.com/derekwinters/lucas-doggiehood/issues/299)/[#414](https://github.com/derekwinters/lucas-doggiehood/issues/414)). Since [#430](https://github.com/derekwinters/lucas-doggiehood/issues/430) that includes zone-built houses: a built zone house gets a real front-walkway edge, so it renders and faces the street like a starting house. A freshly unlocked, **house-less** zone lot still has no `House` entry, so it stays off the graph (its tile's sidewalks/crosswalks still span it, since those derive from the map's roads, not its houses) — which also avoids the catalog throw a house-less lot would otherwise cause. The resulting network is fully connected across every unlocked tile — every node can reach every other node, including onto a newly unlocked cul-de-sac — which Core tests assert directly (BFS reachability). `NeighborhoodLayout.WalkNetwork` still exists as the bare starting-intersection network, used by Core tests that want it in isolation and as `WanderBehavior`'s parameterless-network default.

`WalkNetwork.FindPath` is a small Dijkstra shortest-path over the graph (a priority-queue implementation would be overkill for a graph this size) — used by both wander and walking-home.

## Wander: a node-to-node walk over the network

`WanderBehavior` ([Dog Behavior](../dogs/behavior.md)) no longer does centerline-bounce math on the streets directly. It now random-walks node to node over the sidewalk+crosswalk portion of the network. **A front walkway is a wander candidate only for its own resident dog ([#430](https://github.com/derekwinters/lucas-doggiehood/issues/430)):** `WanderBehavior` carries the wandering dog's own `HouseId`, and a `FrontWalkway` edge is offered only when its owning house (looked up via `WalkNetwork.TryGetFrontWalkway`) is that dog's own house — so a dog may step onto *its own* front walkway, but every other dog keeps excluding **all** front walkways exactly as before. General wander therefore never detours onto a *neighbor's* lot, yard, or door. (A dog with no resident house — the `NoResidentHouseId` default — excludes every front walkway, the pre-#430 behavior.) **A resident dog that has walked all the way up to its own front door returns *back down the same walkway* to the sidewalk ([#517](https://github.com/derekwinters/lucas-doggiehood/issues/517), generalized in [#597](https://github.com/derekwinters/lucas-doggiehood/issues/597)):** the door is the walkway's lot-side endpoint, a walkway-only node the general walkable set excludes, so `WanderBehavior.NextTarget` resolves a resident dog **on the lot (door) side of its own walkway** directly to that door node (via `TryGetFrontWalkway`) rather than through `NearestWalkableNode` — whose sole candidate edge is the walkway back to the attach point. "On the lot side" is detected geometrically against the walkway segment — the dog's projection onto the attach→door line is on the door-side half (up to a small overshoot past the door) *and* within the walkway's own lateral footprint — so it fires for a dog at, a hair short of, or just past the door node, while that narrow lateral bound stops any distant sidewalk node (which can be straight-line closer to a door than that door's own attach point) from ever triggering it. #517 matched only the door node *exactly*; because a dog stops a hair short of or just past the node, that exact match missed and the dog cut diagonally across the lawn to a sidewalk point off to the side (the [#597](https://github.com/derekwinters/lucas-doggiehood/issues/597) regression). Without any of this the door node's straight-line-nearest walkable node is a sidewalk point *across the yard*, and the dog cut diagonally across its own yard to reach it instead of retracing the walkway. Dogs actually *entering* the house or passing through to the backyard stays out of scope — a possible later follow-up. The walk is over the **whole unlocked map** ([#398](https://github.com/derekwinters/lucas-doggiehood/issues/398)), so once a zone is unlocked dogs explore its sidewalks and crosswalks too, not just the starting intersection. A `WanderBehavior` (and `DogView`) binds to a **live network provider** (`() => state.WalkNetwork`) resolved on every hop, so an already-spawned dog picks up newly unlocked tiles the moment the map-derived network grows — no re-spawn.

At each node, the choice between continuing straight and deviating/turning is weighted. Two overloads exist: `WanderBehavior.NextTarget(current, continueWeight, deviateWeight)` takes an explicit override, while the parameterless `WanderBehavior.NextTarget(current)` — what every caller (`DogView`) uses today — derives `continueWeight = 1 - TurnProbability` and `deviateWeight = TurnProbability` from the dog's own `MovementProfile.TurnProbability` (#89). A lower `TurnProbability` (Excited) means a higher continue-weight, i.e. longer straight stretches before a turn, so the per-personality distinction from [Dog Behavior](../dogs/behavior.md#movement-conveys-personality) carries all the way through to wander's actual path shape — both `Speed` and turn pacing now differ for Excited dogs, not just Speed.

## Ground height: sidewalks sit above the road

*Related: [#151](https://github.com/derekwinters/lucas-doggiehood/issues/151)*

The Kenney City Kit Roads tiles model the sidewalk band raised a little
above the road surface (a real curb, not just a color change) — placing a
dog at a single fixed world-Y clipped its legs into that raised mesh
whenever it stood on a sidewalk. `WorldDimensions` now locks
`RoadSurfaceHeight` (0m, the road/crosswalk plane) and
`SidewalkSurfaceHeight` (0.2m, measured directly from the shared kit road
tile mesh) alongside the other world dimensions. `WalkNetwork.GroundHeight
(from, to)` resolves which of the two applies to a hop between two
adjacent network nodes from the specific edge connecting them — a Sidewalk
or FrontWalkway edge resolves to the sidewalk height, a Crosswalk edge to
the road height — rather than from either endpoint node alone, since a
box-corner node (where a crosswalk meets its sidewalks) carries edges of
both kinds and only the edge actually being crossed disambiguates them.
`DogView`'s wander step and `DogSpawner`'s sidewalk spawn point both
consume this Core query instead of hardcoding Y. A companion
`WalkNetwork.SurfaceHeightAt(point)` answers the same road-vs-sidewalk
question for a single arbitrary **point** rather than a graph hop — it
returns `SidewalkSurfaceHeight` when the point falls on a Sidewalk or
FrontWalkway edge's paved-band footprint (within half that edge's width of
the segment) and `RoadSurfaceHeight` everywhere else (flat road lane,
crosswalk, grass). The lost-item **finder ring** consumes it so the ring
sits on the surface the hidden item actually rests on: on the kit's raised
curb+sidewalk band it was previously fixed at the flat ground plane and
rendered buried under that raised mesh, so on-road items showed no
indicator ([#580](https://github.com/derekwinters/lucas-doggiehood/issues/580)).

## Walking home routes over the network

Walking home after accepting a "buy me X" quest ([Quest Content](../quests/quest-content.md)) used to move in a straight line, ignoring streets entirely. Core now computes the actual route with `WalkNetwork.FindPath` from the dog's current position to its house's **front door**, ending via that lot's front walkway ([#128](https://github.com/derekwinters/lucas-doggiehood/issues/128) — the dog arrives at the actual door, which also feeds future quest arrivals); the Unity layer (`QuestDirector`) only consumes the returned waypoint list and walks it frame by frame (`Vector3.MoveTowards` hop to hop) — the Core/Unity split stays intact, per [Testing Strategy](../../engineering/testing.md). Dogs also spawn at their walkway's sidewalk attach point (`DogSpawner`), staggered along the sidewalk so housemates don't overlap.

## Walkway visuals

A front walkway renders as tiled Kenney City Kit Suburban `path-short` pieces — the clean square-paver look, matching the kit sidewalk aesthetic (the kit's stone variants remain an available re-pick for Derek and Lucas). The math lives in Core (`WalkwayTiling`): pieces scale ×10 in width — the same derivation as `WorldBuilder.RoadTileScale`, landing the paver's 0.2 model width exactly on `SidewalkWidth` (2m), which is also the walkway edge's declared width — and along the walkway a whole number of pieces is compressed to cover door → sidewalk exactly (no gap at the door, no overshoot onto the kit road tile's raised sidewalk band). `WorldBuilder` instantiates the pieces verbatim, and falls back to one flat graybox strip when the kit piece can't be loaded — the same primitive-fallback pattern as the roads and houses. The world-build loop delegates to a per-lot `WorldBuilder.BuildWalkway(lot)` helper ([#405](https://github.com/derekwinters/lucas-doggiehood/issues/405)) so a house built mid-game on a zone lot can render its walkway on the same code path; a lot with no front-walkway edge in the network it reads renders nothing, exactly as the loop skips it.

## Explicitly out of scope here

- **Approach-to-rest movement** ([#112](https://github.com/derekwinters/lucas-doggiehood/issues/112)) — `RestBehavior` stays a pure probabilistic state flip with no movement of its own; it doesn't touch the walk network.
(Literal crosswalk striping is no longer deferred — it ships in the kit-art path via the baked-crosswalk intersection meshes: `road-crossroad-path` for a 4-way and `road-intersection-path` for a Tee, see [The crosswalk box](#the-crosswalk-box) above.)
