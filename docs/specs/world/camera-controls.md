# Camera, Navigation & Controls

*Epic: [#14](https://github.com/derekwinters/lucas-doggiehood/issues/14)*

## No player character

There is no visible player-controlled character in the world. The player is an unseen observer viewing the neighborhood from above and interacting with it directly — tapping dogs, houses, and items rather than moving an avatar. ([#19](https://github.com/derekwinters/lucas-doggiehood/issues/19))

## Navigation

Drag/swipe to pan the camera across the neighborhood; pinch to zoom in and out — the same interaction model as panning around a map. Tapping a dog or house triggers its interaction directly. ([#20](https://github.com/derekwinters/lucas-doggiehood/issues/20))

> **How the spec is changing ([#670](https://github.com/derekwinters/lucas-doggiehood/issues/670)).** It used to say *tap* routing is modal-aware → it now says **all** input routing is, pan/pinch/twist/scroll included → because only the tap path ever consulted the modal registry, so a drag on an open dialog panned the map underneath it.

**Invariant — every gesture passes through the one input authority.** Pan, pinch, twist, scroll and tap are all read by a single router and resolved by a single authority that picks exactly one consumer at press-down, in the order modal UI → non-modal UI → world → camera. The camera is an ordinary consumer, offered a gesture only when everything above it has declined. No component polls input or acts on a gesture it was not handed — a second path that happens to check the modal registry today is still not acceptable, because the next one won't. See [Input Authority](../../engineering/input-authority.md).

**No input of any kind reaches the world or the camera while a modal is open.** World routing is modal-aware: when an open dialog/menu sits under the pointer, the tap is absorbed by that UI and the world raycast is skipped — so tapping **Accept** on a quest never also opens a house behind the button, tapping **Close** never re-triggers the thing it sits over ([#422](https://github.com/derekwinters/lucas-doggiehood/issues/422)), and dragging, pinching, twisting or scrolling over an open panel never moves the camera underneath it ([#670](https://github.com/derekwinters/lucas-doggiehood/issues/670)). The authoritative guard is the shared modal registry (`ModalInputGate`) every modal surface registers with on open — including the scrim-less bottom-center conversation panel since [#568](https://github.com/derekwinters/lucas-doggiehood/issues/568), whose same-frame close latch also stops the dismissing tap itself from leaking to the world (see [Shared components → Modal overlays block all input](../ui/shared-components.md#modal-overlays-block-all-input) for the full mechanism). Belt-and-suspenders, the router also bails before any world hit-test when the tap is over a UGUI graphic (`EventSystem.IsPointerOverGameObject`, mouse and touch-`fingerId` overloads — the center-anchored overlays carry a full-screen raycast-blocking scrim, so this reads true anywhere over them) or over the still-IMGUI HUD Settings gear (a screen-space rect check against `HudOverlay.ComputeGearRect`, interim until the gear migrates to UGUI in [#370](https://github.com/derekwinters/lucas-doggiehood/issues/370)).

**The pan bounds grow with the map.** Panning is clamped to the neighborhood's extent, but that extent is not fixed: it is derived from the live tile map (`Doggiehood.Core.World.MapExtent.Covering` — a named margin beyond the outermost tiles) and **re-derived whenever that map changes or is restored** (`CameraController.RecomputeBoundsFromMap`), so the player can always pan over to reach a newly unlocked zone rather than being clamped out of it ([#373](https://github.com/derekwinters/lucas-doggiehood/issues/373)), and can always reach the far side of the neighborhood they loaded ([#691](https://github.com/derekwinters/lucas-doggiehood/issues/691)). The starting bounds derive from the same map-based path (the seeded origin tile), so there is one derivation for both the initial world and every expansion.

> **How the spec is changing ([#691](https://github.com/derekwinters/lucas-doggiehood/issues/691)).** It used to say the pan bounds and the max zoom-out *"recompute when a zone is unlocked"* → it now says both are re-derived from the live tile extent whenever it changes **or is restored**, launch included → because naming one trigger as though it were the whole rule made "recomputes only on unlock" a faithful reading of the spec. Nothing about the camera's reach is persisted and the rig rebuilds its controller from the starting intersection on every scene load, so every launch began clamped to the origin tile ([-42, +42] m, `MaxZoom` 54) however large the saved neighborhood was — you couldn't pan to its southern tiles and couldn't zoom out far enough to see it all, until an unlock happened to fix it for that session.

**Invariant — the camera's reach always matches the live map.** The pan bounds and the maximum zoom-out are derived from the live tile extent and recomputed whenever that extent changes *or is restored* — including at launch, after a save is loaded and green spaces are activated — never only on unlock.

Concretely, every trigger goes through one seam: `CameraReach.SyncToLiveMap(state)` feeds the live `GameState.Map` to Core's `RecomputeBoundsFromMap`. `WorldBootstrap.RestoreMapAndCameraReach` calls it at launch, *after* `MapDataLoader.Apply` has supplied the authored target map and run [#539](https://github.com/derekwinters/lucas-doggiehood/issues/539)'s green-space activation, so the restored road tiles and the auto-placed green spaces are both inside the reach; `ExpansionUnlockDirector` calls the same seam on an unlock. The reach is deliberately **not** persisted — re-deriving it from the map that was just loaded is what makes a relaunch land in the same place a live unlock does. Because the [#165](https://github.com/derekwinters/lucas-doggiehood/issues/165) Home fly-to and [#518](https://github.com/derekwinters/lucas-doggiehood/issues/518)/[#604](https://github.com/derekwinters/lucas-doggiehood/issues/604)'s "Say hi!" both `FocusOn` through these bounds, they were silently clamped back toward the origin on a fresh launch too, and are fixed by the same recompute.

**The maximum zoom-out grows with the map too.** The minimum zoom-in and the default zoom are fixed, but the *max zoom-out* is not: it is re-derived from the same live map extent alongside the pan bounds, in the same `CameraController.RecomputeBoundsFromMap` recompute (a named padding beyond the outermost tiles so the map isn't framed edge-to-edge). So as the neighborhood spreads out with each expansion the player can always zoom out far enough to take the whole current map in at once, rather than hitting a fixed cap — and, since the recompute also runs on the restored map at launch ([#691](https://github.com/derekwinters/lucas-doggiehood/issues/691)), a relaunch never puts the cap back where it started. Whenever the range recomputes, the current zoom is re-clamped into it — mirroring how the position is re-clamped — so an unlock never leaves the camera zoomed out past the new cap ([#510](https://github.com/derekwinters/lucas-doggiehood/issues/510)). The [grass ground plane](world.md#open-space-environment) is **no longer sized to this max-zoom-out reach**: [#536](https://github.com/derekwinters/lucas-doggiehood/issues/536) padded `CameraController.GroundExtentForMap` out to `MaxZoom` so the far zoom-out never framed past the grass, but because `MaxZoom` grows with the map the plane ballooned to dwarf the neighborhood ([#558](https://github.com/derekwinters/lucas-doggiehood/issues/558)). The ground now pads only by the constant `CameraController.BoundsMargin`, and the "never frame past the grass" guarantee moves to a **grass-coloured camera clear colour** (`CameraRig.ApplyConfiguration` sets `clearFlags = SolidColor`, `backgroundColor = Palette.GrassHex`) — so however far the camera zooms out, any pixels beyond the mesh edge read as grass rather than the old blue void seam. That clear colour remains the backstop for pixels genuinely beyond the mesh edge — but it is *not* what the blank band along the bottom of the screen was, and no amount of mesh sizing or colour matching could have been ([#679](https://github.com/derekwinters/lucas-doggiehood/issues/679)); see the clipping invariant below.

> **How the spec is changing ([#679](https://github.com/derekwinters/lucas-doggiehood/issues/679)).** It used to say the "never expose the void" guarantee is carried by *coverage* — a ground mesh sized to the map plus a grass-coloured camera clear colour behind it → it now says the guarantee is carried by the camera's **depth placement**, with the clear colour demoted to a backstop that should never be reached → because the band along the bottom of the screen at high zoom-out was never uncovered ground at all: the ground was there and was being **clipped away** by the near plane. Four coverage-and-colour fixes ([#536](https://github.com/derekwinters/lucas-doggiehood/issues/536) → [#558](https://github.com/derekwinters/lucas-doggiehood/issues/558) → [#570](https://github.com/derekwinters/lucas-doggiehood/issues/570) → [#611](https://github.com/derekwinters/lucas-doggiehood/issues/611)) each shipped and each left the artifact in place, because the spec stated the *outcome* without constraining *how* the rig may be placed — so pinning the set-back to a constant was a legal implementation of a spec whose goal it silently broke.

**Invariant — the visible ground always lies between the camera's clip planes.** The rig's set-back and its near/far clip planes are derived from the live zoom, never pinned to a constant, so at every zoom the whole viewport renders world geometry. Code owns this guarantee; it never depends on serialized scene values.

Concretely, in `Doggiehood.Core.Cameras.CameraRigConfig`: because the ground is pitched away from the view axis, the ground the viewport covers is not a constant-depth slice but a **slab**, of view depth `GroundDepthReach(zoom) = zoom / tan(pitch)` either side of the focus point. `RigDistanceFor(zoom)` sets the camera back by `RigDistance + GroundDepthReach(zoom)`, holding the nearest visible ground a constant `RigDistance` in front of the lens at every zoom; `FarClipFor(zoom)` clears the far edge of the slab by that same named margin. `CameraRig.ApplyControllerState` applies the derived set-back **and** writes `nearClipPlane`/`farClipPlane` on every state change, so the Main scene's serialized values are no longer what the guarantee rests on. This matters most where the two systems meet: since the max zoom-out grows with the map ([#510](https://github.com/derekwinters/lucas-doggiehood/issues/510)/[#524](https://github.com/derekwinters/lucas-doggiehood/issues/524)), a pinned set-back made the failure a function of map size — a single tile of expansion already reached `MaxZoom = 84`, putting the nearest visible ground 24 m *behind* the camera — so the Core tests pin both invariants at the caps `CameraController.RecomputeBoundsFromMap` actually produces across a growing map, and a future change to the cap cannot silently reintroduce the clip.

> **How the spec is changing ([#680](https://github.com/derekwinters/lucas-doggiehood/issues/680)).** It used to say only that tap hit-testing *works at all zoom levels* → it now says how far a tap may reach is **derived from what the camera can see**, never a tuned distance → because the tap ray was pinned to 1000 m while the distance from the lens to the top of the screen grows with the zoom, and the max zoom-out grows with the map. On a neighborhood roughly 940 m across, taps near the top of the screen would have silently stopped registering while taps lower down kept working. Exactly the trap #679 fell into, one layer up: the spec asked for the outcome without constraining how the reach may be chosen, so a magic number was a legal implementation of it.

**Invariant — a tap reaches exactly as far as the camera can see.** Whatever is visible on screen is tappable: the world hit-test's reach is read from the camera's own far clip plane, never from a distance constant. Raising such a constant is not a fix — it is the same defect with a bigger threshold, and it returns the next time the map grows.

Concretely, `TapRouter.RouteTap` raycasts to `camera.farClipPlane`. This composes with the clipping invariant above at no extra cost: `FarClipFor(zoom)` already clears the far edge of the visible ground slab by the named `RigDistance` margin, so "as far as the camera can see" is by construction at least as far as the furthest thing the player could be tapping — at every zoom and every map size, with no second place to keep in step ([#680](https://github.com/derekwinters/lucas-doggiehood/issues/680)).

## Camera angle

Isometric / angled top-down camera — in the spirit of SimCity or Animal Crossing — rather than a straight bird's-eye view or a full free-orbit 3D camera. This shows house facades and roofs and keeps dogs easy to spot and tap. ([#21](https://github.com/derekwinters/lucas-doggiehood/issues/21))

The **pitch (45°) and the orthographic projection are fixed**. The **yaw rotates freely**, driven by a two-finger twist gesture: the neighborhood follows your fingers — twisting clockwise turns the scene clockwise (the camera itself yaws the opposite way), the same "content follows the finger" convention as drag-to-pan. Rotation is continuous — it does not snap to fixed angles and is not clamped to a range. This reopens the original "no free rotation/orbit" decision of #21 for yaw only, while keeping the recognisable angled-down look. ([#203](https://github.com/derekwinters/lucas-doggiehood/issues/203))

> Note: the rotation control (#203) initially left the fixed-angle scene-visibility assumption in place — that content only ever needed to read well at the single fixed yaw. **Camera-facing world markers now track the live camera yaw** so they stay head-on at every rotation: speech bubbles and the map-expansion lock icon share one Core seam (`CameraFacing.Resolve(cameraYaw)` — fixed orthographic pitch, live yaw, zero roll) that the Unity layer re-applies each frame ([#266](https://github.com/derekwinters/lucas-doggiehood/issues/266)). Broader scene *content* that is only authored for the fixed angle (e.g. facade-only art) is a separate follow-on, not covered by the marker-facing work.

## Orientation

The app is **locked to landscape** orientation — it never rotates to portrait — to better show off the neighborhood scene at once. ([#22](https://github.com/derekwinters/lucas-doggiehood/issues/22))

This is one facet of the project's platform target, stated authoritatively once — tablet, landscape, and the 1920×1200 (16:10) UI reference resolution — under [UI Wireframes → Target platform & reference resolution](../ui/index.md#target-platform-reference-resolution). It is enforced in Unity by allowing only the two landscape orientations (portrait disabled, so the tablet auto-rotates between landscape-left and landscape-right but never to portrait) and scaling the UI canvas from that reference with a `CanvasScaler` ([#256](https://github.com/derekwinters/lucas-doggiehood/issues/256)).

## Build checklist

- [ ] Fixed pitch (45°) and orthographic projection, with free twist-driven yaw rotation (continuous, no snapping/clamping)
- [ ] Camera-facing world markers (speech bubbles, map-expansion lock icon) track the live camera yaw and read head-on at every rotation (#266); broader fixed-angle scene-art readability remains a follow-on
- [ ] Pan via drag/swipe within the bounds of the current neighborhood scene (the bounds grow with the map, recomputed from the live tile extent whenever it changes or is restored — [#373](https://github.com/derekwinters/lucas-doggiehood/issues/373))
- [ ] Pinch-to-zoom with a fixed min zoom-in and a max zoom-out that grows with the live map extent (recomputed from the tile extent alongside the pan bounds — [#510](https://github.com/derekwinters/lucas-doggiehood/issues/510)); the current zoom is re-clamped into the new range on each recompute
- [ ] Launching into a multi-tile saved neighborhood yields pan bounds and a `MaxZoom` covering that whole map *before* any unlock happens — and expanding, then relaunching, still does ([#691](https://github.com/derekwinters/lucas-doggiehood/issues/691))
- [ ] At every zoom and every map size the whole viewport renders world geometry — the rig's set-back and its near/far clip planes are derived from the live zoom rather than pinned or left to serialized scene values, so the ground is never clipped into a blank band ([#679](https://github.com/derekwinters/lucas-doggiehood/issues/679))
- [ ] Tap-to-interact hit-testing on dogs and houses works at all zoom levels, with the ray's reach read from the camera's own far clip plane rather than a distance constant — so anything visible on screen stays tappable however far the map grows ([#680](https://github.com/derekwinters/lucas-doggiehood/issues/680))
- [ ] A tap over an open dialog/menu (or its scrim, or the HUD gear) is absorbed by that UI and never reaches a world interactable behind it ([#422](https://github.com/derekwinters/lucas-doggiehood/issues/422))
- [ ] While a modal is open, **no** gesture reaches the camera either — pan, pinch, twist and scroll are all refused, not just taps ([#670](https://github.com/derekwinters/lucas-doggiehood/issues/670))
- [ ] All raw input is read in one place and resolved by one authority that delivers each gesture to exactly one consumer, chosen at press-down ([#670](https://github.com/derekwinters/lucas-doggiehood/issues/670))
- [ ] App is locked to landscape orientation
- [ ] No player avatar/character exists anywhere in the scene
