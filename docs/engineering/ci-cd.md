# CI/CD

*Issues: [#75](https://github.com/derekwinters/lucas-doggiehood/issues/75), [#76](https://github.com/derekwinters/lucas-doggiehood/issues/76), [#80](https://github.com/derekwinters/lucas-doggiehood/issues/80), [#82](https://github.com/derekwinters/lucas-doggiehood/issues/82)*

## PR debug builds

Every PR builds a debug APK via CI — **every** PR, with no path filter, because `Debug APK` is a required status check on `main` and a required check that cannot run deadlocks the PR ([#751](https://github.com/derekwinters/lucas-doggiehood/issues/751), see the invariant under [Test suites](#test-suites-tests)):

- Uses Android's default debug signing — deliberate, and now a deliberate *boundary* rather than a gap ([#75](https://github.com/derekwinters/lucas-doggiehood/issues/75), [#630](https://github.com/derekwinters/lucas-doggiehood/issues/630)): the release keystore is never handed to a `pull_request`-triggered workflow
- Embeds the short commit SHA in the version name (e.g. `0.1.0-a1b2c3d`) so every build is uniquely identifiable
- Applies the `.debug` applicationId suffix ([#80](https://github.com/derekwinters/lucas-doggiehood/issues/80)) via `customParameters: -doggiehoodDebugBuild` on Unity's command line, so it can install side-by-side with a release build on the same device — and **proves it applied** before the artifact is uploaded ([#734](https://github.com/derekwinters/lucas-doggiehood/issues/734), below)
- Uploaded as a GitHub Actions artifact only — no Firebase/Play distribution for now

## Release-candidate builds

When a release-please release PR is open, CI builds a release-candidate APK versioned like `v1.0.0-rc1`. Each time the release PR branch is rebased (new commits land on `main` while it's open), the RC number increments (`rc2`, `rc3`, ...). Once that release ships, the next release-please PR starts over at `rc1`. ([#76](https://github.com/derekwinters/lucas-doggiehood/issues/76))

!!! note "RC numbering design (resolved)"
    release-please's native prerelease support bumps prerelease numbers when *releases* happen, not when the open release PR is rebased, so it can't produce `rc1` → `rc2` across pushes to the same open PR. Instead, `rc-build.yml` derives the RC number itself: it counts that workflow's runs on the release PR's branch since the PR was opened (current run included). Every push to the open release PR adds a run, incrementing the RC; a fresh release PR after a release ships has a later created-at watermark, so the count — and the RC number — starts over at `rc1`. The release PR's `VERSION` file already carries the next version (it's a release-please extra-file), so builds are versioned `v<VERSION>-rc<N>`.

Both PR debug builds and RC builds use debug signing, apply the same `.debug` applicationId suffix ([#80](https://github.com/derekwinters/lucas-doggiehood/issues/80)), and are distributed as GitHub Actions artifacts only. Release builds no longer share that signing ([#630](https://github.com/derekwinters/lucas-doggiehood/issues/630)) — and RC builds deliberately keep it. An RC exists to be *tried*, it already installs side-by-side under its own applicationId, and both workflows that build one are triggered by `pull_request`; handing them the release key would widen its blast radius for no gain.

!!! danger "The `.debug` suffix reached no PR or RC build for as long as it existed ([#734](https://github.com/derekwinters/lucas-doggiehood/issues/734))"
    Both workflows asked for the suffix with a step `env:` entry, `DOGGIEHOOD_DEBUG_BUILD: "true"`, and `DebugApplicationIdBuildProcessor` read it with `Environment.GetEnvironmentVariable`. But `game-ci/unity-builder` does not run Unity in the step's process — it runs it **inside a Docker container**, forwarding only a fixed allowlist of variables (`UNITY_*`, `BUILD_*`, `ANDROID_*`, `CUSTOM_PARAMETERS`, `GITHUB_*`, `RUNNER_*`). A repo-specific variable is set on the runner and never inside the container, so the lookup returned `null`, the hook no-op'd, and every PR and RC APK shipped the bare `com.derekwinters.doggiehood` id. Installed next to a release build it would have **replaced** it rather than sitting beside it — the one thing the suffix exists to prevent. It is the identical defect [#731](https://github.com/derekwinters/lucas-doggiehood/issues/731) found on the emulator flag, on a different flag; unlike that one it produced no visible symptom, because nothing ever compared a debug artifact against anything.

    **Invariant — a debug build requests the suffix through a channel that provably reaches the Unity process, and its artifact proves the suffix applied before it is uploaded.** In practice: the builder's `customParameters` input (forwarded as `CUSTOM_PARAMETERS` and appended verbatim to the `unity-editor` command line), never a step `env:` entry for a repo-specific variable. `DebugApplicationIdBuildProcessor` accepts both channels — the environment variable still works for local and editor builds — but CI uses the command line. Three things enforce it: `.github/scripts/verify_debug_application_id.py` runs in both workflows before `upload-artifact` and fails the job unless the built APK's applicationId is exactly `com.derekwinters.doggiehood.debug`; `test_verify_debug_application_id.py` reads the switch name out of `ApplicationIdSuffix.CommandLineFlag` and fails if either workflow stops passing it or stops running the gate; and `DebugApplicationIdBuildProcessorTests` drives the suffix from the command line alone with the environment variable unset. The gate reuses the emulator gate's binary-manifest reader rather than carrying a second copy of it. Proof that it applied is the gate, plus a `[Doggiehood] Debug applicationId suffix applied:` line in the Unity build log.

> **How the spec is changing (#734).** This page used to say the PR and RC builds apply the `.debug` suffix "via the `DOGGIEHOOD_DEBUG_BUILD` env var". It now says they request it with `customParameters: -doggiehoodDebugBuild` on Unity's command line and verify the finished APK before uploading it, because #734 found the environment variable never crossed into game-ci's build container — so the suffix had in fact never been applied to a PR or RC artifact, and the page was describing a mechanism that did not work.

## Release builds

When a release ships (release-please publishes the `vX.Y.Z` GitHub release), the APK for that tag is built and **attached to the release page** as `doggiehood-vX.Y.Z.apk` — so each release carries its installable build directly, not just as a transient Actions artifact. It is signed with the stable release key ([#630](https://github.com/derekwinters/lucas-doggiehood/issues/630)); see [Release signing](#release-signing-and-in-place-upgrades) below.

Every release also carries a second, **emulator-targeted** asset, `doggiehood-vX.Y.Z-emulator.apk` ([#648](https://github.com/derekwinters/lucas-doggiehood/issues/648)) — so running the game in an x86_64 Android emulator is a download, not a hand-produced one-off. It's built by a second `game-ci/unity-builder` step in the same `build-and-attach` job (into its own `buildsPath: build-emulator`, so the two APKs can't be confused), with `customParameters: -doggiehoodEmulatorBuild` on that step only. That switch is what `EmulatorBuildProcessor` reads to swap in the [emulator build profile](tech-stack.md#target-platform); the device APK above is built first, from the committed ARM64-only defaults, and is unaffected. Both steps are gated on the same license check, so a missing `UNITY_LICENSE` skips both.

!!! danger "A build flag has to reach Unity *inside the container* ([#731](https://github.com/derekwinters/lucas-doggiehood/issues/731))"
    `v0.15.0` shipped with **no APKs at all**. Both builds were device builds, so the pre-upload gate below correctly refused to publish either — a broken release, but the safe failure.

    The cause: the emulator step asked for the variant with a step `env:` entry, `DOGGIEHOOD_EMULATOR_BUILD: "true"`, and `EmulatorBuildProcessor` read it with `Environment.GetEnvironmentVariable`. But `game-ci/unity-builder` does not run Unity in the step's process — it runs it **inside a Docker container**, forwarding only a fixed allowlist of variables (`UNITY_*`, `BUILD_*`, `ANDROID_*`, `CUSTOM_PARAMETERS`, `GITHUB_*`, `RUNNER_*`). A repo-specific variable is set on the runner and never inside the container, so the lookup returned `null`, the processor no-op'd, and the "emulator" APK was a second device build. The emulator variant had therefore **never once applied in CI** since #648 introduced it; until [#706](https://github.com/derekwinters/lucas-doggiehood/issues/706) was fixed it was invisible, because a cache-copied APK is indistinguishable from a profile that didn't apply.

    **Invariant — a build variant is requested through a channel that provably reaches the Unity process, and the artifact proves it applied.** In practice that means the builder's `customParameters` input (forwarded as `CUSTOM_PARAMETERS` and appended verbatim to the `unity-editor` command line), never a step `env:` entry for a repo-specific variable. `EmulatorBuildProcessor` accepts both channels — the environment variable still works for local and editor builds — but CI uses the command line. Two tests enforce it: `test_verify_emulator_build_variant.py` reads the switch name out of `EmulatorBuildProfile.CommandLineFlag` and fails if either release workflow stops passing it (or if the *device* step ever starts), and `EmulatorBuildProcessorTests` drives the whole profile from the command line alone with the environment variable unset. Proof that it applied is the gate below, plus a `[Doggiehood] Emulator build profile applied:` line in the Unity build log.

!!! danger "Two variants in one job need the player build state cleared between them ([#706](https://github.com/derekwinters/lucas-doggiehood/issues/706))"
    `v0.14.0` shipped an `-emulator.apk` that was a **byte-for-byte copy of the device APK** — identical SHA-256, the bare `com.derekwinters.doggiehood` applicationId, `arm64-v8a` libs. Nothing errored; the job went green and uploaded the wrong file, and it only surfaced months later when a field ANR report showed the unsuffixed process name.

    The cause is that `EmulatorBuildProcessor` mutates `PlayerSettings` **in memory only** — deliberately, so nothing leaks into `ProjectSettings.asset` — while Unity's Bee/Tundra player build decides what to rebuild from *on-disk* content hashes. Two builds sharing one `Library` therefore look identical to the incremental system, and the second is served from the first's compiled player (`*** Tundra build success (0.13 seconds), 0 items updated` / `Information on used Assets is not available, since player data was not rebuilt`). Gradle still re-assembles and emits an APK, but from the first build's already-generated project — so the emulator step "succeeded" in 49s against the device build's 9m22s.

    **Invariant — the emulator release asset is never a copy of the device APK, and the device asset never carries the emulator profile.** Two things enforce it. A `sudo rm -rf Library/Bee` step runs before *each* build, so neither variant can ever be served from the other's cached player — in either direction, including across a restored `Library` cache. And `.github/scripts/verify_emulator_build_variant.py` runs after both builds and **before either is uploaded**, failing the release if the two APKs share a SHA-256, if the emulator APK's applicationId doesn't end in `.emulator`, or if either APK's native-lib ABIs aren't exactly what its variant should ship. Its decision logic is unit-tested — on every PR in `ci-tests.yml`, and again in the release job before it's trusted — with the parser pinned against a real `AndroidManifest.xml` pulled from the shipped v0.14.0 asset, so it's proven on genuine Unity/aapt output rather than on a document this repo also authored.

!!! tip "Testing in an emulator or Waydroid? Install the `-emulator.apk`"
    The two release assets are not interchangeable. `doggiehood-vX.Y.Z.apk` is ARM64-only with the project's stock graphics and audio settings; `doggiehood-vX.Y.Z-emulator.apk` is the x86_64 build that carries every [emulator mitigation](tech-stack.md#abis-and-build-variants) — pinned graphics API order, multithreaded rendering off, wide colour gamut off, Unity audio off. Running the device APK under an ARM-translation layer (`libhoudini`/`libndk_translation`) gets you *none* of them.

    Before filing a graphics or ANR report against an emulator, confirm which one is actually installed: `adb shell pm list packages | grep doggiehood` should print `com.derekwinters.doggiehood.emulator`. A bare `com.derekwinters.doggiehood` means the emulator mitigations are **not** active — and, as [#706](https://github.com/derekwinters/lucas-doggiehood/issues/706) found, that can be true even when the `-emulator.apk` asset was the file installed, because releases up to and including `v0.14.0` published an emulator asset that was really the device build. Assets built after that fix are verified before upload, so the suffix is now a trustworthy signal in both directions.

> **How the spec is changing (#731).** This page used to say the emulator asset is built "with `DOGGIEHOOD_EMULATOR_BUILD: "true"` set on that step only", and that the env var "is what `EmulatorBuildProcessor` reads". It now says the step passes `customParameters: -doggiehoodEmulatorBuild` on Unity's command line, and that an environment variable set on a `unity-builder` step never reaches Unity at all. The reason is that #731 found the variable was stranded outside game-ci's Docker container, so the emulator profile had never applied to a shipped artifact — the page was describing a mechanism that did not work.

> **How the spec is changing (#706).** This page used to say a bare `com.derekwinters.doggiehood` in a logcat was *not* evidence the wrong APK was installed, because the missing `.emulator` suffix was an open question. It now says the opposite: the suffix is a reliable indicator, and its absence in the v0.14.0 report was a true positive — the `-emulator.apk` really was the device build, byte for byte. The reason is that #706 resolved the open question against the shipped artifacts rather than by inspection, so the page no longer needs to hedge.

The build-and-attach step lives **inside `release-please.yml`**, as a `build-and-attach` job gated on the release-please job's `release_created` output (`if: needs.release-please.outputs.release_created == 'true'`) and checking out the new `tag_name` output. It runs in the *same* workflow run that publishes the release.

!!! note "Why it's not a separate `release: published` workflow (resolved — [#357](https://github.com/derekwinters/lucas-doggiehood/issues/357))"
    release-please publishes the GitHub release with the default `GITHUB_TOKEN`, and GitHub deliberately does **not** fire workflows from events initiated by `GITHUB_TOKEN` (to prevent recursive runs). A workflow triggered `on: release: [published]` therefore silently never ran for automated releases — only the manual backfill did. Wiring the build into the release-please run itself, gated on `release_created`, sidesteps the token restriction entirely.

`release-build.yml` is retained as the **`workflow_dispatch` backfill**: a manual run that takes an existing release `tag` input and builds + attaches **both** of its APKs — for a release whose publish predates this mechanism, or to re-attach builds on demand. It carries the same reset steps and the same pre-upload verification as the release job, and uploads with `--clobber`, so re-running it for a tag is how a bad asset gets replaced. (It previously built only the device APK, which is why the mislabelled `v0.14.0-emulator.apk` couldn't simply be re-backfilled when [#706](https://github.com/derekwinters/lucas-doggiehood/issues/706) was found.) Its old `release: published` trigger has been removed.

Both paths preserve the **graceful-skip contract**: a "Check for Unity license secret" step gates every build step with `if: steps.license.outputs.present == 'true'`, so a missing `UNITY_LICENSE` secret emits a warning and skips rather than failing the run.

The release **keystore** check deliberately does *not* follow that pattern — it fails the job. The asymmetry is the point: no APK is a tolerable outcome, and a debug-signed APK is not. The first is visible immediately; the second installs fine, looks correct, and quietly makes every future upgrade impossible.

### Release signing and in-place upgrades

Every release asset is signed with one stable, owned release key ([#630](https://github.com/derekwinters/lucas-doggiehood/issues/630)). Android identifies an installed app by its signing certificate: if a new APK's certificate differs from the installed one's, the install is refused outright, and the only way through is to uninstall first — which deletes `doggiehood-save.txt`. The game is offline and local-save-only ([product scope](../specs/product-scope.md)), so that file is the player's only copy. Stable signing is therefore the delivery half of save stability ([#628](https://github.com/derekwinters/lucas-doggiehood/issues/628)): a frozen save schema is worth nothing if the upgrade path deletes the save.

!!! danger "A missing keystore does not fail the build — it silently produces a *different app* ([#630](https://github.com/derekwinters/lucas-doggiehood/issues/630))"
    The dangerous failure here is not an error, it's a success. If a keystore input is mis-wired, a secret is renamed, or the workflow is copied without it, Unity does not complain — it falls back to Android's debug key and emits a perfectly valid APK. That APK installs, runs, and passes every other check in this pipeline. Nothing distinguishes it from a correct build except the certificate inside it, and the damage only appears at the *next* release, on a player's device, as a failed upgrade.

    **Invariant — a published release asset is signed by the pinned release certificate, and by no other key.** Three things enforce it. The release keystore arrives as encrypted Actions secrets ([#629](https://github.com/derekwinters/lucas-doggiehood/issues/629)) — `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_ALIAS_PASSWORD` — and is passed to **every** release build step, device and emulator alike; nothing is ever committed. A "Check for the release keystore secret" step fails the job outright if those secrets are absent, rather than skipping. And `.github/scripts/verify_release_signature.py` runs after both builds and **before either is uploaded**, comparing each APK's certificate against the fingerprint pinned in `.github/release-cert-sha256.txt` and failing the release on any mismatch — naming a debug-key fallback explicitly, because that is the mis-wiring it exists to catch.

    The pinned fingerprint is **public** — it ships inside every APK — which is why it is committed rather than held as a secret. The keystore and its passwords are the secrets, and for a sideloaded APK there is **no key recovery**: lose that keystore and no future version can ever be installed in place again.

    As with the emulator gate, the gate's decision logic is unit-tested on every PR in `ci-tests.yml` and again in the release job before it is trusted. Those tests also pin the *wiring* — that both release workflows still hand the keystore to every build step, and that neither `pr-build.yml` nor `rc-build.yml` references it — so a PR that breaks either fails immediately instead of months later, mid-release.

!!! danger "A gate is only as trustworthy as the realness of the output it was tested against ([#752](https://github.com/derekwinters/lucas-doggiehood/issues/752))"
    v0.16.0 shipped with **no APKs at all**. Both builds succeeded, both were correctly signed, and then this gate refused to read apksigner. It ran `apksigner verify --print-certs` while `parse_apksigner_certs` required the `Number of signers:` header — and apksigner prints that header (with `Verifies` and the `Verified using vN scheme` lines) only under `--verbose`. `--print-certs` alone emits the signer `DN` and `SHA-256 digest` blocks and nothing else: every fact the gate needed to reach a verdict, thrown away for want of a header it never asked for. `gh release upload` never ran, and because the release path attaches APKs to the release page rather than also uploading them as run artifacts, those binaries died with the runner — the release page has zero assets and there is nothing left to inspect.

    Twenty-two unit tests were green at the time. Every apksigner sample among them was hand-authored from the tool's *documented* output shape, and every one was a verbose transcript — describing output the workflow never requested. The suite certified a gate that had never once read a real APK, and could not have.

    **Invariant — a gate that parses another tool's output is tested against at least one fixture captured from a real invocation of that tool, with the exact flags the workflow passes.** A fixture authored from documentation tests the parser against this repo's beliefs about the tool; only a captured one tests it against the tool. Capturing needs no Android SDK — `apt-get download apksigner` yields a jar that runs under the system JRE — which is how `.github/scripts/tests/fixtures/apksigner-verify-print-certs-verbose.txt` and its `-nonverbose` sibling were produced. Both modes are kept: the verbose transcript is the format the invocation now requests and the parser reads, and the non-verbose one is the real output that broke the release, retained so the parser is *proven* to still reject it. The fix was the flags, never a looser parser — the `Number of signers:` cross-check stays exactly as it was, so a genuine future format drift still fails the release closed.

> **How the spec is changing (#630).** This page used to say release builds use "debug signing, same as everything else in the current release scope", with a real keystore listed as deferred under [#75](https://github.com/derekwinters/lucas-doggiehood/issues/75). It now says release and release-candidate builds part company: releases are signed with a stable owned key and verified against a pinned certificate before upload, while PR and RC builds keep debug signing deliberately, so the release key never reaches a `pull_request`-triggered workflow. The reason is that debug signing was only ever survivable *before* anyone had a save worth keeping — once a release is installed, the next differently-signed APK forces an uninstall, and the save goes with it.

## Commit linting

A required CI check lints PR titles against Conventional Commits and fails the PR if it doesn't conform, since release-please's version-bump computation depends on them. ([#82](https://github.com/derekwinters/lucas-doggiehood/issues/82))

## Geometry/tuning literal check

**`geometry-lint.yml`** enforces the [named-values rule](tech-stack.md#geometry-layout-and-tuning-values-are-named-variables) ([#161](https://github.com/derekwinters/lucas-doggiehood/issues/161)): on any PR touching `Assets/**` (or the check itself), it runs `.github/scripts/check_geometry_literals.py`, a conservative backstop that flags f-suffixed float literals of magnitude ≥ 3 sitting in method bodies rather than named declarations. It ratchets against `.github/scripts/geometry_literals_baseline.txt` so pre-existing literals are tolerated while newly introduced ones fail the job; the check's own stdlib-only unit tests run in the same job. Regenerate the baseline as literals get named with `--update-baseline`.

## Test suites (`tests`)

**`ci-tests.yml`** runs the two suites from [Testing strategy](testing.md): a **Core NUnit** job (plain `dotnet test`, no Unity) and a headless **Unity EditMode** job via `game-ci/unity-test-runner`. Both are required status checks on `main`, so the workflow runs on **every** PR with no path filter ([#751](https://github.com/derekwinters/lucas-doggiehood/issues/751)), and its `push:` trigger on `main` is unfiltered too so the commit that lands is covered by the same suites that gated it. The EditMode job still fails outright when the `UNITY_LICENSE` secret is missing, so a required check can't go green without the suite actually running ([#163](https://github.com/derekwinters/lucas-doggiehood/issues/163)).

!!! danger "A required check has to be able to run ([#751](https://github.com/derekwinters/lucas-doggiehood/issues/751))"
    **Invariant — every required status check can actually run on every PR the rule applies to.** A required context that a path filter prevents from ever reporting is not a strict gate, it is a deadlock. Requiring a check and filtering it out of a PR class are contradictory settings, and the contradiction is invisible: nothing fails, the ruleset simply waits forever for a result that structurally cannot arrive and the PR is mergeable only through an owner bypass.

    In practice that means **no `pull_request` path filter at all** on any workflow producing a required context — today `ci-tests.yml`, `pr-build.yml`, `rc-build.yml`, `docs-test.yml` and `pr-title-lint.yml`. A longer allowlist is not the fix: every filter has a PR class it excludes (an allowlist excludes whatever it forgot; a `paths-ignore` excludes any PR confined to the ignored set), and no filter in the tree can see the branch ruleset it would have to stay in sync with. Skip expensive work *inside* a job when it is wasteful — as `rc-build.yml` does with a job-level `if:`, which still reports — but let the check report. Runner minutes are the price; a check that cannot report costs a deadlocked PR.

    `.github/scripts/tests/test_required_checks_reachable.py` enforces it: it hard-codes the six contexts the `main` ruleset requires, maps each to the workflow job that reports under that name, and asserts the trigger fires for a representative diff of every PR class the repo produces — app-code, workflow/script-only, docs-only, and release-please. Adding a context to the ruleset means adding it to that table, which is the moment its reachability gets checked.

> **How the spec is changing ([#751](https://github.com/derekwinters/lucas-doggiehood/issues/751)).** This page used to say `ci-tests.yml` was path-gated to game-code paths (and `pr-build.yml` to app/build files), describing that gating as a plain efficiency measure → it now says a workflow producing a *required* check carries no path filter at all, and states that as an invariant → because two of the six checks `main` requires were filtered out of the PR classes that only touch `VERSION`/`CHANGELOG.md`/the manifest, or only `.github/**` and `docs/**`. Those PRs never got a result, never became mergeable, and every release since the ruleset was created shipped through an owner bypass. Reachability, not thrift, is the rule that governs a required check's trigger.

!!! note "EditMode verdict comes from the results XML, not the runner's exit code ([#534](https://github.com/derekwinters/lucas-doggiehood/issues/534))"
    `game-ci/unity-test-runner` occasionally returns a nonzero docker exit code during editor **teardown** — license return / batch-mode shutdown — *after* a fully green run: the NUnit results XML is written and every test-case reads `result="Passed"`, yet the step is marked failed (it flaked four runs straight on #534, and re-running doesn't help because the flake is in the teardown, not the tests). So the runner step is `continue-on-error`, and **`.github/scripts/verify_editmode_results.py`** re-derives the real verdict from the results XML: it passes only when the suite ran (a `<test-run>` document exists with `total > 0`) and no test failed, and it forgives *only* the teardown exit code. A genuine test failure, a run that died before producing results (the earlier flake mode), or a missing results file still fails the job — the #163 invariant is preserved. The gate's stdlib-only unit tests run in the same job before it's trusted (same posture as the geometry-lint check).

## Docs site build & publish

- **`docs-test.yml`**: runs its `build` job on **every** PR (no path filter) so it can report a status on code-only PRs too, backing the [docs-reconciliation rule](agent-workflow.md):
    - PR touches docs → runs `mkdocs build --strict` to catch broken links/config before merge. No deploy.
    - PR touches no docs → the reconciliation gate fails the PR unless it carries the `skip-docs` label (the deliberate escape hatch for a genuinely doc-irrelevant change).
    - **release-please's auto-generated release PR is exempt.** It only bumps `VERSION`/`CHANGELOG.md`/`manifest.json` and can neither reconcile docs nor self-apply a label, so without an exemption the gate would block every release. It's identified by its deterministic `release-please--branches--*` head branch or its `autorelease: pending` label — either match bypasses the gate.
    - **No transient red on `skip-docs` PRs ([#254](https://github.com/derekwinters/lucas-doggiehood/issues/254)).** `pipeline-dev` can't set `skip-docs` atomically at PR creation — it opens the PR, then labels it a moment later — and the workflow triggers on both `opened` and `labeled`. So the `opened` run would fire before the label lands and fail the gate, then the `labeled` run would re-run and pass; the PR ended green but the superseded failed run still fired a spurious CI-failure webhook on essentially every code-only/tooling PR. To stop that, the gate's decision is a unit-tested script, `.github/scripts/docs_reconciliation_gate.py`: when the triggering payload carries no `skip-docs`, it polls the PR's **live** labels for a short grace window (~45s) before failing, so the same `opened` run observes the just-applied label and passes — **no failing run is ever produced.** Semantics are unchanged: a docs change, the release exemption, or a `skip-docs` present up front still pass, and a genuine code-only PR that never gets docs or the label still fails once the grace window elapses. The live-label fetch is why the workflow grants `pull-requests: read`; the decision matrix (docs-change → pass, release → pass, code-only+`skip-docs` → pass, code-only without either → fail, and the label-landing-during-grace case) is covered by the `gate-tests` job on every PR.
- **`docs-publish.yml`**: path-gated to changes under `docs/`, `mkdocs.yml`, or the workflow file itself. On push to `main` (when docs changed) or on a release tag, builds the site and publishes it with `mike`, versioned to match the app's `VERSION` file, to GitHub Pages.

See the workflow files at `.github/workflows/docs-test.yml` and `.github/workflows/docs-publish.yml`.

## Issue-pipeline workflows

The [AI issue-management pipeline](issue-pipeline.md) adds two workflows, both scoped by path so they don't run on unrelated PRs:

- **`pipeline-tests.yml`**: on any PR touching `.claude/skills/pipeline-*`, runs the pure-Python unit tests for the deterministic pipeline scripts (the gatekeeper command parser, the dev queue selector, and the dashboard renderer's golden snapshot). Stdlib only — no Unity, no pip dependencies.
- **`dashboard.yml`**: a scheduled (and `workflow_dispatch`) job that regenerates the live dashboard issue ([#193](https://github.com/derekwinters/lucas-doggiehood/issues/193)) deterministically from repo state, authenticating its headless issue-body PATCH with the built-in `GITHUB_TOKEN`. It runs a few times a day, shortly after each AI routine, and also `on: issues: [labeled, unlabeled]` so the board refreshes the instant a label changes ([#442](https://github.com/derekwinters/lucas-doggiehood/issues/442)); a constant-group `concurrency` (`cancel-in-progress: false`) serializes the resulting bursts. That trigger fires for human/UI/PAT label moves only — GitHub's no-recursion guard suppresses runs from the automation's own `GITHUB_TOKEN`-authored moves, which the gatekeeper covers by re-rendering #193 inline instead (see `docs/engineering/issue-pipeline.md`).
