    Quest & Economy¶

    Epic: #15

    Core loop¶

    The overall goal is helping dogs around the neighborhood by completing their requests, combined with a daily rotation of active quests. (#23)

    How the pacing is changing (#543, v0.11 playtest fix). Quests used to arrive in one all-or-nothing batch of 2-4 every 8 hours. They now trickle in hourly instead: the same population-scaled target is spread over a 4-hour window (#624 shortened it from 6h), giving a per-hour rate of target / 4. A persisted fractional accumulator (error diffusion, Bresenham-style) handles rates that are not whole numbers — each hour it banks the fractional leftover and only ever adds whole quests, so a 1.25/hr floor neighborhood gets a quest most hours (and a second whenever the carried fraction tips over) and long-run it averages exactly target / 4. The target itself, the ≥1-free-quest guarantee, the headroom/free-dog cap, and the "missed time is a single top-up, no catch-up flood" rule are all unchanged — only the cadence and how many arrive per refresh changed.

    • Pacing: a rotation trickles the neighborhood's active requests in, mixing quest types, a fraction of the target each hour (target / 4 per hour) rather than a fixed batch. Keeps sessions short and gives a reason to return. (#26, #543, #624)
      • Cadence — one hour after the board drops below target (UTC): the recurring refresh is owned by #310 / #543, and since #704 the clock starts when a slot opens rather than running against a full board. The moment the active count falls below TargetActiveCount — a completed quest, or a move-in raising the target — the wait begins, stamped as a persisted UTC timestamp (GameState.QuestRefreshTimerStartedUtc); EconomyNumbers.RefreshInterval (1 hour) later the trickle tops the board up, and the clock restarts if the board is still short or stops entirely once it is full. No clock runs while the board is at target — there is nothing to wait for. UTC — never the device-local clock — so changing the device timezone can neither double-fire nor stall the boundary. It is a boundary check, not a countdown/expiry: nothing is ever removed and no quest can fail (see No pressure below). Missed time is a single top-up: away 1 hour or 4 days, returning triggers exactly one refresh — the accumulator advances a single hour's worth (never per missed hour), so the elapsed span only decides whether to refresh, never how many to add, and there is no catch-up flood and no not-playing-to-hoard exploit.
      • Checked while you play, not only at launch (#704): the boundary used to be evaluated in exactly one place — the scene bootstrap — which made the hourly cadence effectively per app launch: a five-hour session produced no new quests at all, and the only mid-session path that added any was the Debug tab's "Refresh quests now". QuestManager.TickQuests(nowUtc, rng) is the recurring seam (the launch path, EnsureQuestsForLaunch, is the same decision plus onboarding's one-time seed); the Unity layer polls it on a short timer (QuestDirector.PacingTickInterval) and saves only when Core reports something changed. The onboarding gate is unchanged — the rotation stays suppressed until the guided reward chain completes.
      • Per-hour trickle — a fractional accumulator: the number added each hour is target / PacingWindowHours (a named EconomyNumbers constant, 4 hours since #624), so target 6 → 1.5/hr, 12 → 3/hr, and the floor of 5 → 1.25/hr. Fractional rates are handled by a persisted error-diffusion accumulator (GameState.QuestPacingAccumulator, round-tripped by SaveCodec — a legacy save with no questPacingAcc= line loads at 0.0): each hourly boundary it adds the rate, adds floor(accumulator) whole quests, and carries the remainder to the next hour. A quest is never fractional, quiet hours that add 0 are expected and fine, and the long-run rate equals target / 4. The per-refresh min/max fall out of this equation (min 0, max ceil(perHour)) rather than a fixed 2-4 batch.
      • Concurrent-quest cap — population-scaled: a refresh is a top-up toward a target, never a blind add — it adds min(wholeThisHour, target − activeCount, freeDogs), floored at 0 (where wholeThisHour = floor(accumulator + perHour)), so once the neighborhood already holds the target number of uncompleted quests a refresh adds nothing until the player clears some. The leftover fraction is persisted regardless of this clamp, so a quiet hour at the cap can never bank a flood. The target is clamp(round(dogCount / 3), 5, 12) — divisor, floor (5, raised from 3 in #624), and ceiling (12) are all named EconomyNumbers constants. Sample ramp: 8 dogs → 5, 12 → 5, 18 → 6, 24 → 8, 36 → 12, 100 → 12. The ceiling (12) is the playtest flood-control dial — drop it first if a mid-game map feels busy.
      • Always one free quest — soft-lock protection: to prevent a dead-end of 0 coins with every active quest requiring coins to accept, every refresh that adds a quest guarantees the post-refresh active set holds ≥1 free-type quest (the no-cost types, LostItem / PestControl; the paid types are BuyGift / DecorationRequest). If a top-up would otherwise leave an all-paid set, one added quest is forced to a free type. This is enforced only at the refresh boundary, never on quest completion — instant replenish would be an unlimited-coin faucet. A temporary "no free quest" window is fine — including the quiet hours where the trickle adds nothing (completing anything frees a slot and the next hour that adds a quest restores a free option); only locked progress with no exit is prevented.
      • The pacing seam (QuestPacingPolicy): the pacing decisions — ShouldRefresh(nowUtc, state) (has the wait elapsed) and IsBoardBelowTarget(state) (is a wait running at all — #704), TargetActiveCount(state) (cap), PerHourRate(state) / AdvanceAccumulator(...) (the #543 per-hour trickle rate and its whole-quest error-diffusion step), and EligibleSubjectPool(tag, state) (the population-gated purchasable subject pool — see Cost tiers) — live in one Unity-independent Core class that QuestManager asks, rather than reading raw constants inline. All take GameState, so scaling rules driven by dog population change here only, never in the quest engine or the Unity layer.
      • First launch is the exception: the trickle rotation is suppressed during onboarding — the world seeds exactly one easy lost-item quest so the tutorial has a single gentle target. Suppression now extends across the whole onboarding reward-chain: the first normal rotation is held back until the player finishes the four guided steps (quest → upgrade → expand → build), then released the moment the chain completes at the build step. The release seeds an immediate batch, not a single hourly tick (#579). If it ran one hourly-rate refresh from an empty board, a starting neighborhood (target 5 → 1.25/hr, accumulator at 0) would add only floor(1.25) = 1 quest — onboarding would end on a near-empty board that only trickles up over the following hours, leaving little to do. Instead, ReleaseInitialRotation requests the full TargetActiveCount in one shot — skipping the per-hour accumulator throttle for this one release event only — so the player finishes onboarding to a populated board (up to target = 5 ready dogs on distinct houses at the starting population). The same headroom cap, free-dog cap, and ≥1-free-quest guarantee still apply, so the seed can't exceed the target, double-book a dog, or leave an all-paid set; the accumulator and rotation clock are left untouched, so the recurring hourly refresh (#310 / #543) then continues the normal trickle cleanly from that seeded set (headroom already met, so the next boundary adds nothing extra). The single Core decision QuestManager.EnsureQuestsForLaunch picks the pre-chain seed / mid-chain suppression / post-chain refresh at each launch. (#312, #316, #579)
    • Permanence: items/decorations delivered or found through completed quests stay in the world permanently — nothing resets with the daily rotation. (#27)
    • No pressure: quests never expire and there is no timer or fail condition anywhere. (#28)

    Invariant — the neighborhood is durable. Anything the player earned, spent, or was given — every dog living in the neighborhood, every offered or accepted quest, every coin — survives closing the app. Only presentation is session-only: positions, animations, and in-flight view objects. (#704)

    Invariant — a relaunch is never a reset and never a shortcut. Closing and reopening the app removes no active quest and adds none that waiting wouldn't have. Quest pacing is measured in elapsed time, never in launches. This is what rules out the technically-correct-but-wrong fix of "just seed a full batch at launch," which would restore a populated board while quietly turning relaunching into the fastest way to farm quests. (#704)

    Invariant — a restored quest is always something the game can still finish. No quest is ever loaded into a state whose only continuation was a scene object that did not survive the relaunch. A delivery waiting on a truck is resumed at its walk-home leg — same accepted, already-paid job, rejoined at the last step something still drives — because the truck itself is presentation and is gone. Nothing is re-rolled and nothing is re-charged. (#704)

    How the spec is changing (#704). It used to say active quests need no persistence because "the daily rotation regenerates them, and nothing is lost since quests never expire," and that the hourly clock runs from the last rotation → it now says the board itself is saved, and the clock starts only when the board drops below its target and is re-checked while you play → because the "regenerated by the rotation" reasoning stopped holding the moment a refresh became an hourly trickle of one instead of a batch: every relaunch wiped the board and refilled a single quest, which read as "quests take forever to show up." An accepted paid quest made it worse — the coins were deducted durably while the job that reimburses them was not. See Saved state for what is durable and what is deliberately not.

    Currency¶

    Sources/sinks reframed by #626 (v0.13) — see the "getting hired" model below.

    • Sources: currency is earned only by completing dog requests/quests — and, since #675, by the households that arrive off those completions. No idle income, ads, or mini-games for v1.0 (#24). There are three earn shapes:
      • Free-type quests (LostItem / PestControl) — no item to buy, so they pay a flat reward (20 coins, see Numbers).
      • Paid-type quests (BuyGift / DecorationRequest / fence) — the "getting hired to do it" model (#626): you front the item cost when you accept, then completion reimburses it with a margin — round(cost × markup), default markup 1.5×. Every paid job is therefore net positive (toy 30 → +15, pool 40 → +20, fence 100 → +50), and a bigger stake earns a bigger fee. This inverts the pre-#626 model, where gifts/decorations were a coin sink.
      • Move-ins (#675) — a household that fills a vacant house pays a flat 50 coins, once per household. It is not a separate faucet: a move-in is rolled on quest completion, so this income is rate-limited by quest throughput exactly like the two above, and it dilutes on its own as the neighborhood grows (the move-in chance falls with population while quest income rises).
    • Sinks: the only real coin sinks are neighborhood expansion — new streets/houses and house upgrades (Neighborhood Expansion). (#25, #626)
    • No faucet: income stays bounded by the board cap + hourly trickle — each quest pays once, at the rate quests appear, never on demand. Accepting a paid quest still costs coins up front, so a broke player must first earn the stake; the ≥1-free-quest guarantee is the 0-coin bootstrap that always lets them do so. There is no on-completion replenish and no instant-repeat path (#626).

    Numbers (placeholder, expect tuning)¶

    Source: #62

    • A completed free-type quest (LostItem / PestControl) pays a flat 20 coins (EconomyNumbers.QuestPayout). (#623 raised this from 10 to roughly double the early-game earn rate, which comes only from the free quest types; the value lives on TuningConfig so it is slider-tunable in the debug menu.)
    • A completed paid-type quest (BuyGift / DecorationRequest / fence) pays round(cost × markup), default markup 1.5× (EconomyNumbers.PaidQuestPayout, drawing TuningConfig.PaidQuestMarkup) — the earner model above. The item cost is spent on accept and reimbursed-with-margin on completion, so the net gain is payout − cost (toy 30 → 45 / +15, pool 40 → 60 / +20, fence 100 → 150 / +50). A tested invariant guarantees payout > cost for every paid catalog entry, so a paid quest is never a net loss. (#626; markup is slider-tunable in the debug menu.)
    • A completed move-in pays a flat 50 coins (EconomyNumbers.MoveInReward) — per household, not per dog, since one move-in fills exactly one house. 50 is exactly the base house-build cost below, so a new neighbour pays for the next house. It is the second coin source alongside quests, deposited through the same wallet path on the move-in itself; it cannot be farmed, because a move-in is rolled on quest completion rather than on construction (the rate-limit invariant). (#675; slider-tunable in the debug menu.)
    • A typical gift/decoration item costs roughly 30-50 coins — the starter cost tier, the only tier eligible early on (see Cost tiers below). Post-#626 this is the size of the upfront stake you front, not a permanent loss.

    Population-gated cost tiers (decision 2026-07-28, Derek — see #317):

    • Purchasable-quest difficulty scales with total dog population (state.Dogs.Count) — as the neighborhood grows, higher-cost tiers become eligible. All boundaries are draft placeholders, named QuestCostTiers constants (one-line tunes):

      Tier Cost band Eligible once Dogs.Count ≥
      Starter 30-50 coins (today's baseline) 1 (always)
      Mid 60-90 coins 5
      Premium 100+ coins (no ceiling) 10

    v0.4 expansion sinks (decisions 2026-07-14, Derek; tile/build costs rebalanced 2026-08-03 on #540 — see Neighborhood Expansion):

    • Tile unlock (frontier): 200-coin base + 10 per already-unlocked tile (TileUnlock.Cost), no cap — the first unlock costs roughly what it costs to fill the tile it opens (a four-lot tile is 4 × a 50-coin house), then climbs by 10 each. The origin FourWay is excluded, so the first unlock is at the base. (#540 cheapened the base from a flat 100 and added the scaling; #674 then raised the base 50 → 200 so expanding no longer beats building — see Neighborhood Expansion → pricing. This supersedes the retired sequential zone formula 100/200/300…)
    • Building a house: 50-coin base + 5 per 4 houses built (HouseBuildNumbers.Cost), no cap — builds 1-4 at 50, 5-8 at 55, and so on. The 4 starting houses are excluded, so the first build is at the base. (#540 added the scaling; the base is unchanged.)
    • House upgrades: 100 / 200 / 400 coins for levels 2 / 3 / 4.

    #540 in plain English (tile price since superseded by #674): the very first expansion was made as cheap as a house (50, not 100), so a new player gets moving faster; from there both sinks rise gently so growth can't run away — tiles +10 each, houses +5 every 4. Only player actions count toward the curves (the starting FourWay and the 4 starting houses are excluded), and neither curve is capped.

    How the spec is changing (#675). The economy used to have exactly one coin source — completing quests, in two shapes — and a move-in was pure population growth that paid nothing → a completed move-in now also pays a flat 50 coins, once per household, making arrivals a third earn shape → because 50 is exactly what a house costs to build, so a new neighbour pays for the next house, and the early game needs that push now that a tile unlock costs 200 (#674). It is not a new faucet: move-ins are rolled on quest completion, so the rate-limit invariant keeps the income tied to quest throughput and building houses can never farm it.

    #674 in plain English: at 50 a tile, expanding was always cheaper than filling the tile you already had, so the map spread out with empty lots everywhere and the dog population lagged. The unlock now costs 200 — about what four houses cost — so filling a tile before buying the next one is the natural move. The onboarding reward moved to 200 in the same breath, because the guided chain has to pay for its own expand step (below). Nothing else moved: house builds stay 50 (+5 per 4), upgrades stay 100/200/400, and a free quest still pays 20.

    Onboarding reward-chain (decision 2026-07-28, Derek — see Onboarding):

    • Each of the four guided steps pays a flat 200 coins (OnboardingRewardChainNumbers.RewardPerStep, raised from 100 by #674), reusing the quest reward-payout path (a wallet deposit), not the random rotation. The ladder is self-funding: each step's spend comes out of the rewards banked before it, so a player who has earned nothing else clears 100 (upgrade) → 200 (tile unlock) → 50 (build) and finishes on a 450-coin cushion. The binding rung is the expand step — the player reaches it holding 2R − 100, which must cover the unlock, so a 200 unlock needs a reward of at least 150. This is an invariant, not a coincidence: Core derives the minimum viable reward from the live sink prices and a test pins the shipped value at or above it. See Neighborhood Expansion → pricing for the matching sink costs.

    These are starting values, not final balance — expect to tune once the daily-rotation pacing can actually be felt in a playable build. Every one of them is a named constant in Core so playtesting adjustments are one-line changes.

    Item catalog¶

    Source: #190, decided in interview with Derek 2026-07-16.

    The priced catalog and every quest type's subject pool are one source of truth: a single tagged item catalog (ItemCatalog), not per-type hand-maintained lists. Each entry carries:

    • Name
    • Cost — optional. Purchasable items (gift/decoration) carry a cost in the 30-50 range above; find-only items (e.g. a lost puppy) carry none, since they're found rather than bought.
    • Eligibility tags for which quest type(s) it can appear in — Lost, Gift, Decoration. An item can carry more than one tag (a toy or ball is both lost- and gift-eligible).

    Each quest type's subject pool is a query over the catalog's tags (e.g. "every Gift-eligible item"), and the decoration-request options are the Decoration-eligible slice of the same catalog — there is no second, independently maintained item list anywhere. Adding a new item is a single catalog entry with its tags and cost; it then appears automatically in every rotation pool it's tagged for. The 30-50 coin rule is a tested invariant on every Gift- or Decoration-eligible catalog entry priced in the starter tier; a purchasable entry may instead sit in a higher cost tier (mid 60-90, premium 100+), in which case the population gate holds it out of the pool until the neighborhood grows.

    The fence (#318) is the first such higher-tier entry: a Gift-tagged catalog item costing 100 coins (ItemCatalog.FenceItemName/FenceCost), reusing the existing Gift eligibility tag — no new quest type and no fourth eligibility tag. Its 100-coin price places it in the premium tier, so QuestPacingPolicy.EligibleSubjectPool only offers it once the neighborhood reaches the premium population gate (~10 dogs) — that population gate is its "later game" gate, with no bespoke threshold. Unlike every other Gift subject (a package the delivery truck drops at the door), the fence has no delivery flow: accepting it deducts the 100 coins and completes the quest immediately — no delivery truck spawns, the dog does not walk home, and the fence becomes visible right away (no animation). As a paid (Gift-tagged) job it is also an earner: the immediate completion pays back round(100 × 1.5) = 150 coins (net +50), the same cost × markup rule as any other paid quest (#626). Completion records a permanent PlacedItem(houseId, "fence") (the same persistence mechanism as any delivered gift, round-tripped by SaveCodec); the world's backyard fence for that lot then renders from that placed item.

    Cost tiers — population-gated (#317)¶

    Source: #317, decision 2026-07-28 (Derek).

    Purchasable-quest stake ramps with the neighborhood's size so a new player is never offered a request whose upfront cost they can't yet front. This is new cost tiers within the existing 3 quest types, not new quest mechanics — the frozen-types rule holds. There is no hidden level and no new persisted state: total dog population (state.Dogs.Count) is already known, and drives everything.

    Reframed by #626. Since paid quests are earners, a higher tier is a bigger upfront stake and a bigger payback (round(cost × 1.5)), not "unaffordable difficulty". The gate exists so a new player isn't asked to front more coins than they've banked — once they can afford the stake, the pricier job also pays the larger fee. Growth gates the size of the deal, not access to profit.

    • A cost tier is a cost band over the existing item catalog — nothing but a classification of entries already priced. The bands and the population gate that unlocks each are in the Numbers § table above.
    • Eligibility is cumulative and monotonic — reaching a higher population only ever adds tiers to the eligible pool, never removes the cheaper ones, so an established player still gets affordable requests mixed in. The pure QuestCostTiers.EligibleCostTiers(dogCount) function computes this.
    • The gate filters only the purchasable subject pool — BuyGift subjects and decoration-request options. Catalog entries priced above the population-eligible ceiling are excluded from the candidate set, and the injectable RNG picks only from the eligible slice (deterministic per seed). Find-only LostItem subjects (no cost) and PestControl (no item cost) are unaffected.
    • At the starting population the eligible pool is identical to today's (starter tier only), so onboarding and early game are unchanged.
    • The filter is consumed through the pacing seam's QuestPacingPolicy.EligibleSubjectPool(tag, state), which feeds the live ItemCatalog and state.Dogs.Count into QuestCostTiers — one population source of truth shared with #310's availability pacing, not a second parallel signal.

    Quest authoring¶

    Source: #61, implementation tracked in #69. Line-variety model ("Model 2") decided in interview with Derek 2026-07-16, tracked in #189.

    Quests are authored as reusable templates, not hand-written per dog. Each quest type (see Quest Content) has a dialogue template with variable slots:

    • Dog name
    • Item/subject (toy name, decoration type, pest type, etc.)
    • Personality (Dog Behavior) — seasons which opener/closer line is drawn, per the pooled model below

    New quest types (mechanics) beyond the existing set stay deferred to a later version — this section is only about line variety within the existing types, not new mechanics.

    Templates are selected by type and subject (#701). Almost every subject speaks with its type's template. A subject whose resolution mechanic differs from its type's default carries its own pools instead — today only the fence, a "Buy something" purchase that installs in place with no delivery leg (#318). This is not a new quest type or a new mechanic: it is the same type, rendered with lines that describe what it actually does, per the dialogue-matches-mechanic invariant. A new subject-level exception is expected to bring its own pools with it rather than reuse the type's.

    How the spec is changing (#701). Authoring used to say each quest type has a dialogue template, chosen by type alone → it now says a template is chosen by type and subject, with a subject whose mechanic differs from its type's default carrying its own pools → because the fence is a "Buy something" quest with no delivery leg, and inheriting the type's pool had it promising a delivery truck that never comes and describing a lot fixture as a portable gift. Type-alone selection had no seam for a mechanic exception at all, so the wrong promise was already on screen before the engine's fence special-case ran.

    Line variety: pooled openers/closers, uniform random ("Model 2")¶

    For both the opener and the closer, each quest type holds two pools:

    • A default pool of personality-agnostic lines (authoring target ~10-15 lines).
    • A small per-personality pool of personality-specific lines, for whichever personalities we choose to flavor (authoring target ~3-4 lines per personality; 0 is valid — flavoring a personality is optional per type).

    When a quest fires, the candidate set is default pool ∪ this dog's personality pool, and one line is picked uniformly at random per string (not per bucket) — so with ~15 defaults and ~3 Grumpy-specific lines, a Grumpy dog says a Grumpy-specific line only ~1-in-6 of the time. Personality is seasoning, not the default voice; wanting more personality presence means writing more personality-specific lines, never special-casing the weighting. Uniform-per-string is a hard requirement — no single line variant may be allowed to dominate.

    Selection is pure random each fire: no "avoid immediate repeat" memory, no cycle-through, no per-dog or per-session persisted state. The RNG is injectable (constructor/method-seeded System.Random), matching the pattern used by the move-in system, so line selection stays deterministic under test.

    This generalizes what earlier drafts did with a single default line and a single flavored line per personality — same slots, same personality-driven flavoring, just pools instead of one-liners so a given dog doesn't say the identical sentence every time.

    Active-quest reminder pool (#472). Each quest type carries a third pooled line set — a reminder — under the identical Model 2 rules (default pool ∪ this dog's personality pool, uniform-random per string, {dog}/{item} slots, injectable RNG, no persisted state). It renders as a single line, shown when a dog with an already-Accepted quest is re-tapped (see Conversation System and the conversation panel); the opener/closer offer is unchanged. Each template also declares who owes the next action on its accepted quest — the player (lost item, bug problem) or the game (a buy-gift or decoration request, already paid for and in delivery) — and that single declaration drives both the reminder pool's voice and the dismiss pill's label, so the two can never disagree (#708).

    Build checklist¶

    • [ ] Currency balance persists across sessions
    • [ ] Completing a free-type quest (LostItem / PestControl) grants a flat 20 coins; completing a paid-type quest (BuyGift / DecorationRequest / fence) pays round(cost × markup) (default 1.5×) so it is net-positive — the earner model (#626)
    • [x] Paid quests are earners: BuyGift/DecorationRequest/fence completion pays round(cost × TuningConfig.PaidQuestMarkup), every paid catalog entry pays back more than its cost (invariant), free types keep the flat payout, and no on-completion faucet/instant-replenish path is introduced (#626)
    • [ ] Accepting a gift/decoration deducts its cost (30-50 coin range) up front and fails gracefully if the player can't afford it
    • [x] A rotation system trickles quests in hourly toward a population-scaled cap (clamp(round(dogCount/3), 5, 12)), adding target / PacingWindowHours (4h) per hour via a persisted fractional error-diffusion accumulator (GameState.QuestPacingAccumulator, round-tripped by SaveCodec, legacy saves default to 0.0), guaranteeing at least one free-type quest on any refresh that adds a quest so the player is never soft-locked — the cadence, cap, and per-hour trickle all live behind the QuestPacingPolicy seam (#310, #543)
    • [ ] Completed quest state (delivered items, decorations) persists permanently — no reset logic tied to the daily rotation
    • [x] Every uncompleted quest round-trips through SaveCodec in full — status, delivery phase, chosen dialogue, hidden-item position, fronted cost, target house, decoration options — restored without re-rolling, re-charging, or double-booking its dog (#704)
    • [x] A delivery waiting on a truck is restored at its walk-home leg, never in a phase whose only continuation was the (session-only) truck (#704)
    • [x] The refresh clock starts when the board drops below target, is persisted (questTimerUtc=), restarts on a top-up that leaves the board short, and stops while the board is full — away 1 hour or 4 days is still exactly one top-up (#704)
    • [x] The pacing boundary is re-checked while the app is open (QuestManager.TickQuests, polled by QuestDirector), not only at launch (#704)
    • [ ] No quest has a timer, expiration, or fail state anywhere in the system
    • [ ] A quest template data structure exists with slots for dog name, personality-flavored line variant, and item/subject
    • [ ] At least the 3 v1.0 quest types (see Quest Content) are expressed as templates, not hard-coded per-dog text
    • [ ] Template selection is by quest type and subject — a subject whose resolution mechanic differs from its type's default (today the fence) renders from its own pools, and every other subject still renders from the unchanged type template (#701)
    • [x] Opener and closer lines are drawn from a default pool ∪ per-personality pool, uniform-random per string, via an injectable RNG — no anti-repeat memory or per-dog persisted state (#189)
    • [x] All quest subject pools (and decoration-request options) are queries over one tagged item catalog — no per-type parallel item lists; every Gift/Decoration-eligible entry costs 30-50 coins, find-only entries carry no cost (#190)
    • [x] Purchasable-quest cost tiers are gated by total dog population — QuestCostTiers.EligibleCostTiers(dogCount) is monotonic (starter-only at 1, +mid at 5, +premium at 10), the pacing seam's EligibleSubjectPool excludes catalog entries above the population-eligible ceiling, and LostItem/PestControl are unaffected; no new persisted state (#317)
    • [x] The fence is a Gift-tagged, 100-coin (premium-tier) catalog entry — offered only at ≥10 dogs via the population gate; accepting it deducts the cost and completes immediately with no delivery truck and no walk-home, recording a permanent PlacedItem(houseId, "fence") that drives the lot's backyard fence visibility and round-trips through SaveCodec (#318)
